# IT Trend 작성 규칙

## 프로젝트 동기화 자료

- 작업 공간에 `sources/`가 있으면 그 아래 파일은 ChatGPT 프로젝트에서 동기화된 읽기 전용 참고 자료로 취급한다.
- 동기화 자료는 편집, 이름 변경, 이동, 삭제하지 않는다. 다음 작업 생성 시 교체될 수 있으므로 결과물도 그 위치에 저장하지 않는다.

## 목표와 독자

- 독자는 기술을 의사결정과 운영에 연결해 이해하려는 기업 IT 실무자다.
- 글은 기술의 기능 목록이 아니라, 왜 지금 중요한지, 어디에 적용되는지, 어떤 제약이 있는지를 설명한다.
- 기술 도입을 권고할 때는 적용 조건과 검증 방법을 함께 제시한다. 특정 기업의 활용 가능성을 실제 도입 사례처럼 쓰지 않는다.
- `혁신`, `게임체인저`, `완전히 바뀐다`와 같은 과장된 표현은 근거가 있을 때만 제한적으로 사용한다.

## 사실·출처

- 회사 발표, 제품 기능, 수치, 출시일, 시장 현황처럼 바뀔 수 있거나 검증 가능한 주장은 신뢰할 수 있는 원문으로 확인한다. 공식 문서·논문·공식 기술 블로그를 우선한다.
- 본문에는 각주, 링크, 매체명 등 출처 표기를 넣지 않는다. 출처는 글 마지막 `## 출처`에만 사람이 확인할 수 있는 제목과 링크로 남긴다. 출처가 지원하지 않는 결론을 붙이지 않는다.
- 출처는 공식 자료·보도자료·신뢰할 수 있는 언론·기술 문서·연구 자료 중심으로 구체적으로 쓴다.
- 해석·전망·제안은 사실과 구분해 `가능성`, `검토할 수 있다`, `이 글의 분석`처럼 표현한다.
- 자료가 충분하지 않으면 단정하지 않는다. 불확실성을 남기거나 사용자에게 추가 자료를 요청한다.

## 문체와 구조

- 자연스러운 한국어 산문으로 쓴다. 존댓말보다 설명형 문체를 기본으로 하며, 과장된 홍보 문구와 불필요한 영어 혼용을 피한다.
- 도입부에서는 독자가 마주한 변화나 질문을 먼저 제시한다. 본문은 결론이 드러나는 `##` 제목으로 구성하고, 결론에서는 핵심 판단을 다시 연결한다.
- 소제목 앞에 `1.`, `2.`, `도입:`, `결론:` 같은 번호나 역할 표기를 붙이지 않는다. 소제목만 읽어도 글의 논리와 판단이 드러나는 리딩 메시지형 문장으로 쓰고, 모든 소제목은 `중요성`, `변화`, `적용 범위`, `판단 기준`처럼 명사형으로 종결한다.
- 한 문단에는 하나의 주장과 근거를 둔다. 전문 용어는 처음 등장할 때만 짧게 설명한다.
- 표는 세 개 이상의 항목을 비교할 때만 사용한다. 표 바로 앞이나 뒤에서 비교의 의미를 설명한다.
- 인용은 최소화하고, 장문의 외부 원문을 번역·재현하지 않는다.
- 업체와 기술을 나열하는 데 그치지 않고, 각각이 어떤 기술·시장·아키텍처 흐름을 대표하는지 해석한다.
- SaaS 주제에서는 SI·컨설팅 업체와 실제 SaaS 제품 제공 업체를 구분한다. 기능표보다 기술 흐름과 데이터·플랫폼·아키텍처 관점의 의미를 우선한다.

## 기존 원고 보존과 개정 검수

- 사용자가 제공한 완성본, 이전 대화의 원문, 또는 명시적으로 기준으로 지정한 초안은 **기준 원고**로 취급한다. 새 글을 별도로 다시 쓰거나 요약본으로 대체하지 않는다.
- 개정 전에는 기준 원고의 제목, 도입 논지, 각 소제목, 기업·프로젝트 사례, 표, 이미지, 결론, 출처를 목록으로 확인한다. 개정 후에는 이 목록과 대조해 삭제·축약·일반화된 항목을 명시적으로 검수한다.
- 특정 기업, 서비스, 사업 맥락(예: 고객사가 지정한 기업의 클라우드·데이터센터·AI 플랫폼 관점)은 글의 핵심 범위다. 이를 일반적인 사례로 바꾸거나 제거하지 않는다. 사실 확인이 필요하면 공식 자료로 보강하고, 실제 도입 사례가 아니라면 `활용 가능성` 또는 `검토 방향`임을 명확히 쓴다.
- 새 구조·문체 규칙을 적용하더라도 핵심 논지, 사례, 표, 시사점은 보존한다. 어느 항목을 제외해야 한다고 판단하면 먼저 이유와 영향을 사용자에게 제시해 승인을 받는다.
- 기준 원고에 없는 내용은 근거를 확인한 뒤 보강으로만 추가한다. 원문보다 짧아지는 개정은 분량이 아니라 논지·사례·의사결정 정보가 보존됐는지를 기준으로 검토한다.

## 콘텐츠 형식

- 발행 파일은 `src/content/posts/` 아래 `.md` 또는 `.mdx`로 둔다. 초안은 `writing/`에 유지한다.
- 필수 frontmatter는 `title`, `description`, `pubDate`, `category`, `slug`다. `tags`는 주제 검색에 도움이 되는 소수의 일관된 키워드만 사용한다.
- `slug`는 URL 계약이다. 이미 발행한 글의 slug를 임의로 바꾸지 않는다.
- 본문 마지막에는 `## 출처`를 둔다. 이미지 출처와 라이선스가 필요한 경우에도 이곳 또는 이미지 캡션에서 명확히 밝힌다.

## 이미지와 자산

- 이미지는 관계, 흐름, 비교를 이해시키는 경우에만 추가한다. 장식용 이미지는 사용하지 않는다.
- 생성 이미지는 본문에서 검증해야 하는 긴 문구·수치·로고를 포함하지 않도록 한다. 정확한 레이블이 필요하면 Markdown 표나 텍스트를 사용한다.
- 웹 이미지는 재사용 권한 또는 사용 허가가 분명한 경우에만 내려받아 사용한다. 외부 URL을 직접 hotlink하지 않는다.
- 자산은 `public/images/contents/it-trend/<topic>/`에 저장하고 `/images/contents/it-trend/<topic>/<filename>`으로 참조한다. alt 텍스트와 `*그림 N. ...*` 형식의 캡션을 넣는다.

## 완료 기준

- frontmatter, 문단 흐름, 표, 링크, 이미지 경로와 출처를 다시 확인한다.
- `pnpm build`를 `codes/`에서 실행해 Astro 콘텐츠 검증을 통과시킨다.
- 작성 단계에서는 커밋·푸시·배포하지 않는다. 검수와 배포는 `it-trend-review-deploy` 단계에서 처리한다.

## Google Docs 산출물

사용자가 Google Docs 문서를 요청한 경우에만 다음 형식을 적용한다.

- A4와 상하좌우 72pt 여백을 사용한다.
- 제목은 Arial 24pt 굵게·짙은 남색·가운데 정렬로, 제목 아래 작성일은 `IT Trend  |  [작성일]` 형식의 Arial 10.5pt 굵게·파란색·가운데 정렬로 둔다.
- 본문은 Arial 10.5pt, 줄 간격 122%, 문단 아래 7pt를 기본으로 한다. 소제목은 Arial 16pt 굵게·짙은 남색이며, 다음 본문과 분리되지 않게 한다.
- 출처는 본문과 같은 서식의 불릿 목록으로 쓴다.
- 새 문서는 Google Drive 폴더 `1upNwdQ9E-tj9OiSFgNvfYo5PlR13gD7x`에 저장한다.
- Google Drive 파일 제목은 `[yyyy-mm-dd] <기사 제목>` 형식을 사용하며, 날짜는 게시글의 `pubDate`를 ISO 형식으로 쓴다.
