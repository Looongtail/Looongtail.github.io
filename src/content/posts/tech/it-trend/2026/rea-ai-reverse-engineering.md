AI 코딩 에이전트는 이제 새 코드를 작성하는 일을 넘어, 이미 배포된 소프트웨어의 동작을 조사하는 작업에도 쓰이기 시작했다. 이 변화는 레거시 시스템의 이해와 보안 연구에는 유용할 수 있다. 동시에 프로그램을 배포하는 기업에는 핵심 기능을 어디에 두고, 무엇을 어떻게 검증·보호할지라는 새로운 질문을 던진다.

최근 공개된 REA(Reverse Engineer Anything)는 이 변화를 보여 주는 사례다. REA는 원본 소스 코드가 없는 애플리케이션, 실행 파일, 실행 중인 프로그램을 대상으로 코딩 에이전트가 분석 도구에서 근거를 수집하도록 돕는다. 핵심은 AI가 갑자기 완전한 디컴파일러가 되었다는 데 있지 않다. 기존 분석 도구와 에이전트의 탐색·설명·구현 작업이 하나의 흐름으로 연결된다는 데 있다.

## 분석 도구와 에이전트 결합에 따른 진입 경로의 변화

전통적인 리버스 엔지니어링은 디컴파일, 디버깅, 호출 관계 추적, 실행 관찰을 결합해 프로그램의 동작을 추론하는 작업이다. Ghidra, IDA, Hopper 같은 도구가 제공하는 결과를 읽고 가설을 검증하려면 전문 지식과 시간이 필요했다.

REA는 이를 대체하는 독립적인 분석 엔진이라기보다, 코딩 에이전트가 기존 도구와 분석 결과를 사용할 수 있게 하는 연결 도구에 가깝다. 프로젝트 문서는 에이전트가 코드, 참조 관계, 실행 중 관찰한 결과를 수집하고 특정 기능을 설명하거나 별도 구현을 만드는 흐름을 제시한다. 실행 파일, JavaScript·Electron 애플리케이션, 브라우저와 실행 중인 프로그램 등 대상에 따라 분석 방법과 필요한 도구가 달라진다.

이 흐름을 단순화하면 `질문 → 코드·실행 근거 수집 → 가설 검증 → 설명 또는 별도 구현`으로 볼 수 있다. 자연어로 목표를 지정할 수 있다는 점은 반복 탐색의 부담을 낮추지만, 근거의 해석과 결론의 검증까지 자동으로 보장하지는 않는다.

## 레거시 분석과 보안 연구의 활용 범위

원본 소스 코드나 최신 설계 문서가 없는 시스템은 운영과 현대화의 비용을 높인다. 이때 특정 파일 변환 규칙, 외부 인터페이스, 호출 흐름처럼 범위가 명확한 기능을 조사하는 일은 유용한 출발점이 될 수 있다. 분석 결과는 새 시스템의 요구사항을 확정하는 답이라기보다, 인터뷰·테스트·문서 검토로 확인할 가설로 관리하는 편이 안전하다.

보안 연구에서도 코드를 실행하지 않고 살피는 정적 분석과 실제 실행 관찰은 오래전부터 중요했다. AI 에이전트는 의심스러운 호출 경로를 찾고, 문자열·참조·네트워크 동작 같은 확인 결과를 묶어 조사 대상을 좁히는 역할을 할 수 있다. 그러나 에이전트의 설명만으로 취약점이나 악성 행위를 확정해서는 안 된다. 재현 가능한 테스트, 독립적인 도구 결과, 숙련된 분석자의 검토가 필요하다.

| 활용 영역 | AI 기반 분석이 도울 수 있는 작업 | 별도로 확인할 사항 |
| :--- | :--- | :--- |
| 레거시 현대화 | 특정 기능의 입출력·호출 흐름 파악 | 업무 규칙, 예외 처리, 운영 이력 |
| 호환성·연동 | 파일 형식과 공개되지 않은 동작의 조사 | 라이선스·계약 및 법적 허용 범위 |
| 보안 연구 | 분석 우선순위 설정, 코드·실행 근거 정리 | 재현성, 오탐, 안전한 격리 환경 |
| 제품 검증 | 버전 사이의 동작 차이 탐색 | 성능·안정성·보안·전체 기능 동등성 |

이 표의 공통점은 분석 결과가 곧 최종 결론은 아니라는 점이다. 특히 여러 작업이 동시에 처리되는 상황, 서버에서 처리되는 업무 규칙, 여러 시스템에 나뉜 상태, 예외 처리까지 포함한 전체 제품을 한 번에 재현하는 일은 특정 기능을 조사하는 것과 난도가 다르다.

## 소프트웨어 분석 부담의 감소와 완전한 재현의 한계

디컴파일 결과는 원본 소스 코드의 복원본이 아니다. 프로그램을 실행 가능한 형태로 만드는 과정에서 사라진 변수명, 주석, 구성 요소의 경계, 설계 의도는 보통 그대로 되살아나지 않는다. 화면과 정상 입력에서 비슷하게 동작하는 구현도 오류 상황, 성능, 여러 작업의 동시 처리, 접근 제어에서는 원본과 다를 수 있다.

AI가 분석 결과를 자연스러운 설명과 코드로 바꾸는 과정에는 추가적인 오류 가능성도 있다. 제한된 코드 경로나 실행 결과를 전체 동작으로 일반화하거나 함수의 책임을 잘못 해석할 수 있기 때문이다. 따라서 중요한 평가 기준은 생성된 코드의 양이 아니라, 어떤 근거를 확인했는지, 어떤 조건에서 비교했는지, 확인하지 못한 범위가 무엇인지가 되어야 한다.

기업 환경에서는 이를 위해 분석 요청의 목적과 범위를 제한하고, 근거·명령·결과를 보관하며, 독립된 테스트로 재현성을 확인하는 절차가 필요하다. 분석 에이전트의 결론과 검증 도구의 결과를 같은 것으로 취급하지 않는 통제가 핵심이다.

## 인디게임 데모 취소가 보여 주는 제품 공개 전략의 변화

AI 기반 복제에 대한 우려는 대형 상용 소프트웨어만의 문제가 아니다. 2026년 10월 16일, 게임 *Drunken Goddess Reflux*의 개발·퍼블리싱 측은 10월 19일 공개 예정이던 데모를 취소하고 제한된 참가자를 대상으로 한 폐쇄형 플레이 세션으로 전환한다고 공지했다. 공지와 관련 보도는 데모의 표현·게임플레이를 AI나 다른 도구로 빠르게 모방해 출시 전 유사작을 낼 수 있다는 우려를 배경으로 제시했다.

이 사례를 REA에 의한 직접적인 소스 코드 복제 피해로 해석해서는 안 된다. 그런 인과관계를 보여 주는 근거는 확인되지 않는다. 다만 공개 데모가 피드백과 마케팅의 수단인 동시에 기능·자산·상호작용을 노출하는 배포물이라는 점, 그리고 빠른 재구현에 대한 우려만으로도 공개 방식을 바꿀 수 있다는 점은 분명하다.

![분홍색 머리의 캐릭터와 게임 제목이 담긴 Drunken Goddess Reflux의 Steam 공식 헤더 이미지](/images/contents/it-trend/rea-ai-reverse-engineering/drunken-goddess-reflux-header.jpg)

*그림 2. Drunken Goddess Reflux의 Steam 상점 공식 헤더 이미지. 본문에서 다루는 데모 공개 계획 변경 사례의 게임을 식별하기 위한 자료다. 이미지: Steam 상점 페이지.*

제품팀에는 단순한 공개·비공개 선택보다 더 세밀한 판단이 필요하다. 사용자 기기에서 실행되는 프로그램에 무엇을 포함할지, 서버에서 보호할 핵심 규칙은 무엇인지, 데모에서 허용할 관찰 범위는 어디까지인지, 유출·모방이 발생했을 때 어떤 대응 증거를 확보할지를 함께 검토해야 한다. 모든 기능을 서버로 옮기는 방식은 비용과 지연 시간, 오프라인 지원, 사용자 경험의 손실을 수반할 수 있으므로 만능 해법은 아니다.

## 기술적 방어를 넘어선 제품 구조와 운영 통제 중심의 보호 전략

사용자에게 배포되는 프로그램은 일정 수준의 분석 가능성을 피하기 어렵다. 코드를 읽기 어렵게 만드는 난독화와 프로그램 변조를 막는 기술은 분석에 드는 노력을 늘릴 수 있지만, 핵심 경쟁력이 되는 데이터·의사결정 규칙·서비스 운영 능력 전체를 보호하지는 못한다.

따라서 보호 전략은 기술적 방어만이 아니라 제품 구조와 운영의 문제로 봐야 한다. 서버와 사용자 프로그램의 책임을 구분하고, 민감한 비밀값이 배포물과 로그에 남지 않도록 하며, 접근 제어와 이상 징후 탐지를 운영해야 한다. 외부 프로그램을 실제로 실행하며 분석할 때는 악성 동작과 환경 오염을 막기 위해 격리 환경과 최소 권한도 필요하다.

법률과 계약의 검토도 별도 축이다. 한국 저작권법은 프로그램코드역분석에 관한 규정을 두고 있지만, 도구를 쓸 수 있다는 사실이 분석 결과의 복제·배포·상업적 이용을 자동으로 허용하지는 않는다. 분석 대상의 라이선스, 계약 조건, 적용 법률을 목적과 지역에 맞게 검토해야 하며, 중요한 사업 판단은 법률 전문가의 자문이 필요하다.

## 분석 가능성보다 중요한 검증과 보호의 설계

REA 같은 도구는 소프트웨어를 이해하기 위해 들이는 탐색 부담을 낮출 수 있다. 레거시 분석, 호환성 연구, 보안 조사처럼 정당한 목적의 업무에서 특히 유용할 가능성이 있다. 반대로 소프트웨어를 제공하는 기업에는 이미 배포된 결과물을 어떻게 보호하고, 분석에서 얻은 결과를 어떻게 검증·통제할지의 중요성을 높인다.

기업이 먼저 정할 것은 도입 여부 하나가 아니다. 분석이 허용되는 대상과 목적, 에이전트가 접근할 수 있는 데이터와 도구, 근거 보관 방식, 재현 테스트와 사람의 승인 지점, 결과물의 법적 활용 범위다. AI가 분석을 빠르게 만들수록 이 경계와 검증 절차를 명시하는 일이 제품 구조와 보안 운영의 일부가 된다.
