AI 코딩 에이전트는 새 코드를 작성하는 일을 넘어, 이미 배포된 프로그램이 어떻게 동작하는지 조사하는 작업에도 쓰이기 시작했다. 과거 리버스 엔지니어링은 전문 분석 도구와 숙련된 분석자의 경험에 크게 의존했다. 이제는 에이전트가 분석 도구를 호출하고, 함수·문자열·호출 관계·실행 기록을 연결해 특정 기능에 대한 설명과 재현 후보를 만들 수 있다.

이 변화는 레거시 시스템을 이해하고 보안 문제를 조사하는 데는 유용할 수 있다. 반면 프로그램을 배포하는 기업에는 다른 질문을 던진다. 사용자가 받은 실행 파일에서 어느 정도까지 기능을 파악할 수 있는가, 핵심 경쟁력은 어디에 두어야 하는가, 분석과 재구현 결과를 어떤 기준으로 검증하고 관리할 것인가가 그 질문이다.

[REA(Reverse Engineer Anything)](https://github.com/morluto/rea)는 이 변화를 보여 주는 오픈소스 프로젝트다. REA의 의미는 AI가 단독으로 모든 소프트웨어를 복원한다는 데 있지 않다. 기존 분석 도구가 제공하던 근거와 AI 코딩 에이전트의 탐색·설명·구현 작업을 하나의 흐름으로 묶는 데 있다.

## REA의 작동 원리와 분석 근거의 연결

리버스 엔지니어링은 프로그램 자체를 살펴보며 동작 원리를 알아내는 작업이다. 실행 파일을 사람이 읽기 쉬운 의사 코드로 바꾸는 디컴파일, 실행을 멈추며 값을 확인하는 디버깅, 함수 호출 관계 추적, 실제 실행 관찰이 함께 쓰인다. 분석자는 이 결과를 조합해 어떤 입력이 어느 경로를 거쳐 어떤 결과를 만드는지 추론한다.

REA는 이런 기존 작업을 없애는 독립적인 분석 엔진이라기보다, 코딩 에이전트가 기존 도구와 분석 결과를 사용할 수 있게 하는 연결 도구에 가깝다. 프로젝트 문서가 제시하는 출발점은 한 기능에 대한 질문이다. 에이전트는 대상 프로그램의 코드와 참조 관계, 실행 중 관찰한 결과를 수집하고, 그 결과를 다음 조사 단계의 근거로 사용한다. 마지막에는 발견한 내용을 설명하거나 제한된 범위에서 별도 구현을 만들어 원래 동작과 비교할 수 있다.

REA는 CLI와 MCP(Model Context Protocol)를 통해 이런 분석 기능을 에이전트의 작업 흐름에 연결한다. 지원 환경에서는 Ghidra, IDA, Hopper처럼 이미 널리 쓰이는 분석 엔진을 활용할 수 있으며, 실행 파일뿐 아니라 JavaScript·Electron 애플리케이션, .NET 어셈블리, 웹 애플리케이션과 일부 실행 중 분석까지 대상이 될 수 있다. 다만 모든 파일 형식과 플랫폼에서 같은 수준의 결과가 나오는 것은 아니다. 실제 분석 범위는 설치된 분석 엔진, 대상 프로그램의 보호 방식, 실행 환경, 그리고 에이전트가 접근할 수 있는 자료에 따라 달라진다.

이 흐름은 `기능 질문 → 대상별 분석 → 근거 연결 → 가설 검증 → 설명 또는 별도 구현`으로 정리할 수 있다. “이 프로그램을 복제해 달라”보다 “이 버튼은 어떤 조건에서 값을 바꾸는가”, “이 화면의 복사 기능은 어느 코드로 이어지는가”처럼 확인 가능한 기능 하나가 분석과 검증에 적합하다.

![REA가 DX-Ball 실행 파일의 소리 위치 계산 함수를 조사하고, 호출 관계·명령어·상수를 바탕으로 C 코드로 재구성한 공식 분석 다이어그램](/images/contents/it-trend/rea-ai-reverse-engineering/rea-dx-ball-investigation.svg)

*그림 2. REA의 공식 DX-Ball 조사 다이어그램. 실행 파일의 한 함수를 조사하고, 호출 관계·명령어·상수를 근거로 C 코드로 재구성한 뒤 원본과 대조하는 과정을 보여 준다. 이미지: REA 공식 사례.*

| 분석 대상 | REA가 에이전트에 제공할 수 있는 근거 | 확인해야 할 핵심 질문 |
| :--- | :--- | :--- |
| 실행 파일과 라이브러리 | 명령어, 의사 코드, 문자열, 함수와 호출 관계 | 어떤 입력이 어느 함수로 들어가 어떤 계산을 거치는가 |
| JavaScript·Electron 애플리케이션 | 모듈 관계, 가져오기, 경로, 프로세스 간 통신, 네이티브 의존성 | 화면의 기능이 어느 코드와 운영체제 기능으로 이어지는가 |
| 브라우저와 실행 중인 프로그램 | 선택한 활동의 실행 기록과 여러 실행 결과의 비교 | 조건이 달라질 때 어떤 코드 경로와 동작 차이가 나타나는가 |

REA가 제공하는 것은 완성된 정답 코드가 아니라, 에이전트가 읽고 확인해야 할 근거와 위치다. 에이전트가 함수에 그럴듯한 이름을 붙이거나 의사 코드를 자연스러운 문장으로 설명할 수는 있다. 그러나 그 설명이 원래 설계 의도와 같은지, 다른 조건에서도 유지되는지는 별도의 테스트와 사람이 확인해야 한다.

이런 근거 중심 분석은 AI가 잘못된 내부 로직을 그럴듯하게 설명하는 문제를 줄이려는 시도이기도 하다. 코드 위치, 함수, 파일, 실행 결과처럼 확인 가능한 단서를 남기고, 분석하지 못한 부분은 추론 또는 미확인 정보로 구분해야 한다. 그러나 근거가 존재한다고 해서 분석이 완전하다는 뜻은 아니다. 확인된 코드 경로 밖에 다른 실행 조건이 있거나 서버 측 처리 로직이 별도로 존재할 수 있으므로, 실제 구현에 활용할 때는 추가 검증이 필요하다.

## 공식 사례가 보여 주는 기능 분석과 재현의 범위

REA의 공식 사례는 전체 제품을 즉시 복제하는 모습을 보여 주기보다, 한 기능을 작은 질문으로 쪼개고 근거를 이어 붙이는 과정을 보여 준다. 실제 제품의 기능은 화면 하나나 함수 하나로 끝나지 않으며, 데이터 형식·예외 처리·권한·서버 처리·운영 환경까지 연결되기 때문이다.

Windows 계산기 사례에서 REA는 퍼센트 버튼의 동작을 조사한다. `200 + 10%`와 `200 × 10%`가 다른 결과를 내는 이유를 찾기 위해 실행 파일의 분기와 호출 관계를 확인한다. 덧셈·뺄셈 경로에서는 앞선 값의 일정 비율을 더하고, 곱셈·나눗셈 경로에서는 입력값을 비율로 바꾼다는 규칙을 각각 추적한다. 계산식 자체보다 분기와 상수, 호출자를 함께 확인해야 한 기능의 규칙을 설명할 수 있다는 점이 핵심이다.

Notion 데스크톱 사례는 더 복잡한 애플리케이션에서의 추적 방식이다. 복사 기능은 화면에서 단순한 호출처럼 보이지만, 실제로는 화면 쪽 API가 내부 통신을 통해 메인 프로세스로 요청을 보내고, 메인 프로세스가 송신자를 확인한 뒤 운영체제의 클립보드 기능을 호출하는 경로를 거친다. REA는 포장된 JavaScript에서 이 통신 채널과 양쪽의 코드를 찾고, 감싸진 함수를 풀어 실제 호출 관계를 따라간다.

DX-Ball 사례는 실행 파일의 한 함수를 별도 코드로 재구성할 때 필요한 검증 수준을 보여 준다. 에이전트는 벽돌의 위치가 소리의 좌우 위치 값으로 바뀌는 계산을 조사한다. 처음 얻은 의사 코드만으로는 입력값과 계산식이 충분히 드러나지 않기 때문에, 호출자와 명령어, 상수를 추가로 살펴본다. 재구성한 C 함수는 원래 실행 파일의 결과와 독립적으로 비교한다. 재현의 신뢰도는 자연스러운 설명이 아니라 어떤 입력과 결과를 어느 범위까지 대조했는가에 달려 있다.

| 공식 사례 | 조사 대상 | 확인한 동작 | 보여 주는 분석 원칙 |
| :--- | :--- | :--- | :--- |
| Windows 계산기 | 퍼센트 버튼의 실행 경로 | 연산자에 따라 달라지는 계산 규칙 | 입력·분기·상수·결과를 함께 추적 |
| Notion 데스크톱 | 복사 기능의 코드 경로 | 화면 API부터 내부 통신, 시스템 클립보드까지의 연결 | 포장된 코드에서도 호출 관계를 단계별로 확인 |
| DX-Ball | 소리 위치 계산 함수 | 실행 파일의 계산을 C 함수로 재구성하고 별도 비교 | 재구현은 분석과 독립 테스트를 함께 요구 |

이 사례들은 REA 프로젝트가 자체적으로 제공한 시연이다. 도구의 작업 방식을 이해하는 근거로는 적합하지만, 임의의 상용 소프트웨어를 같은 수준으로 분석·재현할 수 있다는 성능 보장은 아니다. 대규모 제품에서는 여러 기능이 데이터베이스, 서버, 외부 서비스, 접근 권한, 업데이트 체계와 연결되므로 한 기능의 재현 결과를 제품 전체의 복제로 확대해석하면 안 된다.

## 레거시 분석과 보안 연구의 활용 범위

AI 기반 리버스 엔지니어링이 가장 현실적으로 쓰일 수 있는 영역은 원본 소스 코드나 최신 문서가 부족한 시스템을 이해하는 일이다. 오래된 프로그램의 특정 파일 변환 규칙, 외부 인터페이스, 화면과 데이터 처리의 연결 관계를 조사하면 현대화 프로젝트의 질문을 더 구체적으로 만들 수 있다. 분석 결과는 요구사항을 자동으로 확정하는 답이 아니라, 현업 인터뷰·테스트·문서 검토로 확인할 가설로 관리해야 한다.

호환성 확보도 중요한 활용 영역이다. 기존 제품이 만들던 파일 형식이나 메시지 구조를 이해하고, 지원이 끝난 시스템과 새 시스템을 연결하려는 경우가 여기에 해당한다. 관찰 가능한 입출력을 맞추는 일과 실제 내부 구조를 복제하는 일은 구분해야 한다. 상호 운용성을 위한 분석이 기술적으로 가능하더라도, 분석 대상의 라이선스와 계약 조건, 적용 법률은 별도로 검토해야 한다.

보안 연구에서는 코드를 실행하지 않고 살피는 정적 분석과 실제 실행 관찰이 오래전부터 중요했다. AI 에이전트는 의심스러운 호출 경로를 찾고, 문자열·참조·네트워크 동작을 묶어 조사 우선순위를 정하는 데 도움을 줄 수 있다. 그러나 에이전트의 설명만으로 취약점이나 악성 행위를 확정해서는 안 된다. 재현 가능한 테스트, 독립적인 도구 결과, 숙련된 분석자의 검토가 필요하다.

| 활용 영역 | AI 기반 분석이 도울 수 있는 작업 | 별도로 확인할 사항 |
| :--- | :--- | :--- |
| 레거시 현대화 | 특정 기능의 입출력·호출 흐름 파악 | 업무 규칙, 예외 처리, 운영 이력 |
| 호환성·연동 | 파일 형식과 공개되지 않은 동작의 조사 | 라이선스·계약 및 법적 허용 범위 |
| 보안 연구 | 분석 우선순위 설정, 코드·실행 근거 정리 | 재현성, 오탐, 안전한 격리 환경 |
| 버전 검증 | 버전 사이의 동작 차이 탐색 | 성능·안정성·보안·전체 기능 동등성 |

## 소프트웨어 분석 부담의 감소와 완전한 재현의 한계

AI가 분석 도구의 문턱을 낮춘다고 해서 디컴파일의 한계가 사라지는 것은 아니다. 디컴파일 결과는 원본 소스 코드의 복원본이 아니다. 프로그램을 실행 가능한 형태로 만드는 과정에서 사라진 변수명, 주석, 구성 요소의 경계, 설계 의도는 보통 그대로 되살아나지 않는다. 화면과 정상 입력에서 비슷하게 동작하는 구현도 오류 상황, 성능, 여러 작업의 동시 처리, 접근 제어에서는 원본과 다를 수 있다.

데스크톱 애플리케이션의 화면과 네트워크 요청을 분석하더라도 서버에서 처리되는 업무 규칙과 데이터, 모델, 운영 정책까지 확인할 수 있는 것은 아니다. 오프라인 환경에서 정상 입력을 처리하는 기능을 재현했다고 해서 장애 상황, 계정별 권한, 대량 처리, 보안 정책에서도 같은 결과를 낸다고 볼 수 없다.

AI 에이전트에는 추가적인 해석 오류가 생길 수 있다. 제한된 코드 경로나 실행 결과를 전체 동작으로 일반화하거나, 함수의 역할을 잘못 이름 붙이거나, 찾지 못한 예외 경로를 생략할 수 있다. 중요한 평가 기준은 생성된 코드의 양이나 데모의 완성 속도가 아니다. 어떤 근거를 확인했는지, 어떤 조건에서 원본과 비교했는지, 아직 확인하지 못한 범위가 무엇인지를 남기는 일이 더 중요하다.

## 인디게임 데모 취소가 보여 주는 제품 공개 전략의 변화

AI 기반 복제에 대한 우려는 대형 상용 소프트웨어만의 문제가 아니다. 2026년 10월 16일, 게임 *Drunken Goddess Reflux*의 개발·퍼블리싱 측은 10월 19일 공개 예정이던 데모를 취소하고 제한된 참가자를 대상으로 한 폐쇄형 플레이 세션으로 전환한다고 공지했다. 공지와 관련 보도는 데모의 표현·게임플레이를 AI나 다른 도구로 빠르게 모방해 출시 전 유사작을 낼 수 있다는 우려를 배경으로 제시했다.

이 사례를 REA에 의한 직접적인 소스 코드 복제 피해로 해석해서는 안 된다. 그런 인과관계를 보여 주는 근거는 확인되지 않는다. 다만 공개 데모가 피드백과 마케팅의 수단인 동시에 기능·자산·상호작용을 노출하는 배포물이라는 점, 그리고 빠른 재구현에 대한 우려만으로도 공개 방식을 바꿀 수 있다는 점은 분명하다.

공개 범위를 결정할 때는 무엇을 사용자 기기에서 실행되게 할지, 서버에서 보호할 핵심 규칙은 무엇인지, 데모에서 어느 정도의 관찰과 기록을 허용할지, 유출·모방이 발생했을 때 어떤 대응 증거를 확보할지를 함께 판단해야 한다. 모든 기능을 서버로 옮기는 방식은 비용과 지연 시간, 오프라인 지원, 사용자 경험의 손실을 수반할 수 있으므로 만능 해법은 아니다.

## 기술적 방어를 넘어선 제품 구조와 운영 통제 중심의 보호 전략

사용자에게 배포되는 프로그램은 일정 수준의 분석 가능성을 피하기 어렵다. 코드를 읽기 어렵게 만드는 난독화와 프로그램 변조를 막는 기술은 분석에 드는 노력을 늘릴 수 있지만, 핵심 경쟁력이 되는 데이터·의사결정 규칙·서비스 운영 능력 전체를 보호하지는 못한다.

따라서 보호 전략은 기술적 방어만이 아니라 제품 구조와 운영의 문제로 봐야 한다. 서버와 사용자 프로그램의 책임을 구분하고, 민감한 비밀값이 배포물과 로그에 남지 않도록 하며, 접근 제어와 이상 징후 탐지를 운영해야 한다. 분석하기 어려운 코드를 만드는 것보다, 노출돼도 치명적이지 않게 기능과 데이터를 배치하는 설계가 더 중요한 경우가 많다.

외부 프로그램을 실제로 실행하며 분석할 때는 반대 방향의 보안 위험도 있다. 신뢰할 수 없는 실행 파일이 분석 환경을 오염시키거나 설정 파일과 인증 정보를 읽으려 할 수 있기 때문이다. 격리된 환경, 최소 권한, 네트워크 통제, 분석 도구와 의존성의 공급망 점검은 분석자의 기본 통제가 되어야 한다.

법률과 계약의 검토도 별도 축이다. 한국 저작권법은 프로그램코드역분석에 관한 규정을 두고 있지만, 도구를 쓸 수 있다는 사실이 분석 결과의 복제·배포·상업적 이용을 자동으로 허용하지는 않는다. 분석 대상의 라이선스, 계약 조건, 적용 법률을 목적과 지역에 맞게 검토해야 하며, 중요한 사업 판단은 법률 전문가의 자문이 필요하다.

## 분석 가능성보다 중요한 검증과 보호의 설계

REA 같은 도구는 소프트웨어를 이해하기 위해 들이는 탐색 부담을 낮출 수 있다. 레거시 분석, 호환성 연구, 보안 조사처럼 정당한 목적의 업무에서 특히 유용할 가능성이 있다. 그러나 이 도구의 가치는 AI가 모든 프로그램을 자동으로 복제한다는 주장에 있지 않다. 분석 결과를 근거와 함께 남기고, 특정 기능의 동작을 더 빠르게 가설화·검증할 수 있게 하는 데 있다.

소프트웨어를 제공하는 기업의 과제도 단순한 도입 찬반이 아니다. 분석이 허용되는 대상과 목적, 에이전트가 접근할 수 있는 데이터와 도구, 근거 보관 방식, 재현 테스트와 사람의 승인 지점, 결과물의 법적 활용 범위를 정해야 한다. AI가 분석을 빠르게 만들수록 이 경계와 검증 절차를 명시하는 일이 제품 구조와 보안 운영의 일부가 된다.

앞으로의 경쟁력은 기능을 만드는 비용만으로 결정되지 않을 수 있다. 이미 배포된 소프트웨어를 이해하고 유사 기능을 구현하는 비용도 낮아질 수 있기 때문이다. 그래서 기업은 무엇을 코드에 담을지, 무엇을 서비스와 데이터·운영 능력으로 보호할지, 그리고 분석 결과를 어떤 검증 기준으로 다룰지를 함께 설계해야 한다.
