AI 코딩 도구의 역할은 코드 자동 완성에서 여러 파일을 수정하고 테스트를 작성하는 작업 수행으로 확대되고 있다. 개발자는 요구사항을 전달하고 결과를 검토하는 방식으로 작업할 수 있게 됐지만, 이것이 개발 과정 전체의 비용을 없애지는 않는다. AI가 생성한 변경을 이해하고 기존 시스템과의 관계를 파악하며 설계 의도에 맞는지 확인하는 일은 여전히 사람의 책임이다.

이 변화에서는 코드 작성보다 구현 결과를 이해하는 과정이 새로운 병목이 될 수 있다. 여러 모듈에 걸친 API, 데이터 모델, 비즈니스 로직 변경을 Git Diff만으로 검토하면, 개발자는 파일 사이의 연결 관계를 다시 머릿속에서 조립해야 한다. AI가 한 번에 만드는 변경 범위가 커질수록 이 부담도 커진다.

이 문제의식에서 등장한 오픈소스가 **Whiteboard**다. devdotfast가 개발한 Whiteboard는 사람과 AI 코딩 에이전트가 하나의 작업 공간에서 소프트웨어 구조, 구현 내용, 설계 결정을 함께 검토하도록 만든 데스크톱 애플리케이션이다. 핵심은 AI가 코드를 더 많이 쓰도록 하는 데 있지 않다. AI가 수행한 작업을 사람이 구조적으로 이해하고 질문할 수 있는 인터페이스로 다시 표현한다는 데 있다.

## 최신 AI 코딩 흐름에서의 출발

Whiteboard는 AI 코딩 에이전트가 구현을 수행하고, 사람이 설계와 결과를 검토하는 흐름이 빠르게 자리 잡는 시점에 나온 초기 OSS다. 저장소는 2026년 8월 18일 생성됐고, 프로젝트는 9월 24일 Show HN을 통해 데스크톱 애플리케이션의 MIT 라이선스 공개를 알렸다. 이 시점은 AI가 코드를 생성하는 능력 자체보다, 사람이 넓어진 변경 범위를 어떻게 이해하고 검증할 것인가가 개발 도구의 중요한 질문으로 떠오른 시기와 맞닿아 있다.

공개 직후의 관심은 도구가 다루려는 문제가 개발자에게 얼마나 가까운지를 보여 주는 초기 신호로 볼 수 있다. 다만 별이나 포크 수는 제품의 안정성·보안성·기업 환경 적합성을 증명하지 않는다. 특히 이 프로젝트는 빠르게 변하는 초기 단계이므로, 도입 판단에서는 공개 활동보다 실제 워크플로우와 운영 조건을 검증해야 한다.

| :--- | :--- | :--- |

이 글에서 확인한 수치는 Whiteboard가 아직 성숙한 표준 도구라기보다, 최신 AI 코딩·리뷰 흐름 속에서 빠르게 주목받는 프로젝트임을 보여 준다. 따라서 기업은 관심 지표를 도입 근거로 삼기보다, 실제 변경 검토 시간이 줄어드는지와 기존 품질 절차를 보완하는지를 평가해야 한다.

## 구현 결과 이해의 중요성

기존 개발 환경에서 개발자는 요구사항을 분석하고 설계를 만든 뒤 코드를 직접 작성하며 구현 맥락을 축적했다. 코드 리뷰도 작성자가 설계 의도를 알고, 검토자가 변경된 코드를 읽는 흐름을 전제로 한다. 반면 AI 코딩 에이전트는 짧은 시간에 여러 모듈을 고칠 수 있다. 리뷰를 시작하는 시점에 사람은 변경 결과를 받았지만, 전체 구현 경로를 충분히 이해하지 못했을 수 있다.

Git Diff는 파일의 어느 줄이 바뀌었는지는 정확히 보여 주지만, 그 변경이 시스템의 어떤 동작과 연결되는지까지 자동으로 설명하지는 않는다. 예를 들어 API 변경이 요청 검증, 서비스 로직, 저장소 계층, 테스트에 함께 영향을 주면, 검토자는 각 파일을 오가며 업무 흐름을 재구성해야 한다.

Whiteboard의 접근은 이 순서를 바꾼다. 개별 파일에서 출발하는 대신 변경의 구조와 설명을 먼저 보고, 필요한 지점에서 실제 코드로 내려가게 한다. 이는 코드 중심 탐색을 대체한다기보다, 아키텍처와 업무 흐름이라는 새로운 진입점을 추가하는 방식이다.

## 공통 설계 공간의 역할

Whiteboard는 Claude Code나 Codex 같은 기존 에이전트를 대체하는 새로운 코딩 모델이 아니다. 사용하던 에이전트를 연결하면 에이전트가 SDK를 통해 애플리케이션 내부 Canvas에 자신의 작업을 표현하는 구조다. 개발자는 그 설명을 살펴보고, 필요한 부분을 선택해 추가 질문을 하거나 다시 그리도록 요청할 수 있다.

공식 Quickstart도 이 역할을 분명히 한다. 애플리케이션을 설치하고 에이전트를 연결한 뒤, 현재 작업 브랜치를 최신 `main`과 비교해 결과를 Whiteboard에서 열도록 요청하는 흐름이다. 즉 새로운 저장소나 개발 프로세스를 강제하기보다, 기존 Git 작업과 에이전트 사용 방식 위에 설계·리뷰 공간을 더한다.

## 코드 연결 시각화의 활용 범위

Whiteboard의 대표 기능은 시각화 요소에서 구현 코드로 이동하는 코드 연결 시각화다. 에이전트는 시퀀스 다이어그램, 엔터티 관계도, 데이터 흐름 또는 자신의 작업 기록 일부를 표현할 수 있고, 개발자는 요소를 선택해 관련 코드로 이동할 수 있다.

예를 들어 AI가 새로운 API를 구현하면서 요청 처리, 데이터 검증, 서비스 로직, 데이터베이스 접근 구조를 바꿨다고 하자. 기존 방식에서는 Controller부터 Repository까지 여러 파일을 차례로 읽으며 흐름을 파악한다. Whiteboard에서는 먼저 전체 흐름을 검토한 뒤 특정 처리 단계가 궁금할 때 해당 코드로 이동할 수 있다. 검토의 중심이 파일 목록에서 아키텍처와 업무 흐름으로 옮겨가는 셈이다.

이 방식은 데이터 파이프라인이나 마이크로서비스처럼 관계가 복잡한 시스템에서 검토 보조 수단으로 활용할 수 있다. 데이터 소스, 변환, 적재 대상의 관계나 서비스 간 API 의존성을 먼저 살핀 뒤 구현을 확인하는 식이다. 다만 이는 기능을 바탕으로 한 적용 시나리오다. Whiteboard가 특정 업무 도메인의 구조를 자동으로 정확하게 분석한다고 해석해서는 안 된다.

전체 아키텍처에서 특정 변경으로, 다시 실제 함수와 코드로 내려가는 탐색 순서는 대규모 시스템을 이해하는 방식과 잘 맞는다. Whiteboard는 이 수준 사이의 이동을 줄이려 한다. 그러나 시각화와 Diff가 실제 구현을 정확히 반영하는지 여부는 사람이 원본 코드와 테스트로 확인해야 한다.

## 변경 의미 중심의 리뷰 인터페이스

Whiteboard에는 Rust 기반의 AST 인지형(구문 구조 인지형) Diff 뷰어가 포함돼 있다. 일반 Git Diff가 추가·삭제된 텍스트 라인을 중심으로 보여 준다면, 이 뷰어는 코드 구조를 이용해 검토의 밀도를 조정한다. 긴 추가 함수는 의사 코드로 요약하고, 테스트와 문서 변경은 기본적으로 접거나 숨기는 설정을 제공한다. 표시 정책은 WASM 플러그인 방식으로 확장할 수 있다.

관련 프로젝트인 `devdotfast/diffr`는 이 기능을 실험적 알파 단계로 설명한다. 특히 요약 기능은 지원 모델과 설정에 제약이 있으며, 플러그인 API도 계속 바뀔 수 있다. 따라서 Semantic Diff는 프로그램이 요구사항을 만족하는지 자동으로 증명하는 기능이 아니다. 사람이 중요 변경을 빠르게 찾고, 필요할 때 원본 코드와 테스트를 열어 보도록 돕는 리뷰 인터페이스로 이해하는 편이 적절하다.

AI가 생성한 변경에는 핵심 로직뿐 아니라 보조 함수, 테스트, 문서가 함께 포함되는 경우가 많다. 이때 모든 줄을 같은 비중으로 읽기보다 외부 인터페이스, 비즈니스 규칙, 예외 처리, 의존성 변경부터 확인하는 것이 효율적일 수 있다. 구조를 활용한 접기와 요약은 이런 검토 순서를 지원할 수 있지만, 요약 때문에 가려진 세부사항이 없는지 확인하는 책임은 검토자에게 남는다.

## 의사결정 맥락의 검토 가능성

AI 에이전트의 결과물은 코드만으로 완전히 설명되지 않을 때가 있다. 개발자가 API 구현을 요청했는데 에이전트가 새로운 라이브러리를 추가하거나 데이터 모델을 바꿨다면, 변경 자체와 함께 왜 그런 판단이 필요했는지도 검토해야 한다.

Whiteboard의 Decision Log는 에이전트가 자신의 작업 기록을 조회하고, 요구사항과 자율적으로 내린 판단을 Whiteboard 요소에 연결하도록 만든 기능이다. 개발자는 요구사항이 어떤 방식으로 구현됐는지와 에이전트가 어떤 선택을 했는지를 같은 검토 공간에서 살필 수 있다. 기존 코드 리뷰에서 변경 이유를 작성자에게 사후 질문하던 흐름을 보완하는 시도다.

*그림 2. Whiteboard의 실제 리뷰 결정 패널. 출처: devdotfast Whiteboard 공식 저장소, MIT License.*

장기 운영되는 기업 시스템에서는 결과 코드만큼 설계 판단의 맥락이 중요하다. 성능 제약, 데이터 정합성, 다른 시스템과의 의존 관계를 이해하지 못하면 이후 변경에서 같은 위험이 반복될 수 있다. 다만 현재 기능을 장기 아키텍처 의사결정 관리 시스템이나 완전한 감사 추적 체계로 확대 해석해서는 안 된다. 기록의 완전성과 정확성, 보존 정책은 실제 도입 환경에서 별도로 검증해야 한다.

## 설계 검토 워크플로우의 적용 조건

Whiteboard는 구현 변경보다 설계 검토와 코드 리뷰 단계에 적합하다. 새로운 기능 또는 모듈 변경 뒤 에이전트에게 인터페이스, 사용 예시, 변경 배경을 설명하도록 요청하고, 그 결과를 바탕으로 설계와 코드의 관계를 살피는 방식이다. 다이어그램으로 전체 구조를 파악한 뒤 함수 구현을 열어 보고, 구조화된 Diff에서 핵심 변경을 읽고, Decision Log에서 판단 근거를 확인할 수 있다.

개발자는 설명이나 구조가 부족한 부분을 선택해 에이전트에 다시 표현하도록 요청할 수 있다. 이 과정의 주체는 AI가 아니라 사람이다. 어떤 구조가 필요하고 어디까지 설명돼야 하는지를 개발자가 결정해야 한다.

현재 Whiteboard에서는 소스 파일을 직접 수정할 수 없다. 따라서 구현 변경은 연결된 코딩 에이전트나 기존 개발 도구에서 수행하고, Whiteboard는 설계와 검토의 작업 공간으로 쓰는 역할 분리가 필요하다. 여러 저장소를 하나의 리뷰에서 탐색하는 기능도 충분히 지원되지 않으며, 공유한 리뷰는 수정 후 자동 동기화되지 않아 다시 공유해야 한다.

## 초기 OSS 도입의 검증 기준

Whiteboard는 MIT 라이선스로 공개됐으며 로컬 체크아웃을 대상으로 동작한다. 공식 문서는 익명 텔레메트리에 코드, Diff, Whiteboard 텍스트, 프롬프트, 모델 출력이 포함되지 않으며 사용자가 이를 끌 수 있다고 설명한다. 팀용 호스팅 제품은 계획 단계이고, 프로젝트는 자체 호스팅 가능성을 유지하겠다는 방향을 밝히고 있다.

그러나 기업 보안 검토는 Whiteboard 자체에만 머물 수 없다. 연결한 코딩 에이전트와 모델 제공자가 어떤 데이터를 전송·보관하는지, 리뷰 데이터가 어디에 저장되는지, Code OSS 업스트림 보안 패치가 어떤 주기로 반영되는지를 함께 확인해야 한다. 초기 오픈소스의 공개 활동이나 관심도는 대규모 조직의 안정성과 지원 수준을 보장하지 않는다.

도입 여부는 화면의 직관성만으로 판단하기보다, 실제 팀의 변경 이해 시간, 리뷰에서 발견한 결함, 리뷰 품질, 기존 IDE·Git 워크플로우와의 마찰을 기준으로 작은 범위에서 측정하는 편이 현실적이다. 기존 코드 리뷰, 테스트, 정적 분석, 보안 검사는 계속 유지해야 한다.

## 인간의 이해를 지키는 개발 환경

Whiteboard의 의미는 또 하나의 AI 코딩 에이전트가 등장했다는 데 있지 않다. AI가 구현 속도를 높이는 과정에서 사람이 놓치기 쉬운 설계 맥락과 변경 구조를 다시 보여 주는 작업 공간을 제안했다는 데 있다.

기업 IT 관점에서는 아키텍처 리뷰, 코드 변경 분석, 신규 개발자의 시스템 이해, AI 에이전트가 수행한 작업의 설명 등 여러 과정에서 활용 가능성을 검토할 수 있다. 다만 구조적으로 보기 좋은 다이어그램이 올바른 구현을 뜻하지는 않는다. AI가 만든 설명도 코드, 테스트, 요구사항과 대조해야 한다.

결국 AI 코딩의 생산성은 AI가 얼마나 빨리 구현하는가만으로 결정되지 않는다. 사람이 결과를 이해하고, 설계 판단에 계속 참여하며, 필요한 검증을 수행할 수 있는가가 함께 중요하다. 다음 글에서는 이 관점을 바탕으로 AI와 인간의 설계 협업, 코드 리뷰의 변화, 그리고 구현 정확성을 검증하기 위해 필요한 기술적 조건을 살펴본다.
