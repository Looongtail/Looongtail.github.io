생성형 AI의 빠른 발전 뒤에는 오픈소스 소프트웨어(OSS)가 있다. PyTorch와 Hugging Face를 비롯한 프레임워크와 라이브러리, Kubernetes와 같은 클라우드 네이티브 플랫폼은 AI 모델을 개발하고 배포하는 기반으로 활용돼 왔다. 많은 기업이 공개된 기술과 개발자 생태계를 활용하면서 AI 도입 속도도 함께 빨라졌다.

최근에는 이 관계가 반대 방향으로도 작동하기 시작했다. 오픈소스가 AI 발전을 지원하는 데 그치지 않고, AI가 다시 오픈소스의 코드 작성과 테스트, 문서화, 유지보수에 참여하고 있다. 이 변화는 OSS 개발의 진입장벽을 낮추는 동시에, 누가 어떤 방식으로 코드를 검증하고 책임질 것인지라는 새로운 과제를 만든다.

## 오픈소스 위에서 성장한 AI 생태계

현재의 AI 개발 환경은 단일 기업의 기술만으로 구성되지 않는다. 모델 학습에는 PyTorch 같은 프레임워크가 사용되고, 모델과 데이터셋을 공유하는 과정에는 Hugging Face 생태계가 활용된다. 개발된 모델을 실제 서비스로 운영하려면 Kubernetes, 컨테이너, 오픈소스 데이터 플랫폼과 추론 엔진도 함께 필요하다.

기업 입장에서도 모든 기술을 직접 개발하기보다 검증된 OSS를 조합해 AI 플랫폼을 구성하는 방식이 일반적이다. 따라서 AI 시장의 확대는 모델 성능뿐 아니라 이를 둘러싼 오픈소스 생태계의 지속성과 호환성에 밀접하게 연결돼 있다.

## 이제 AI가 오픈소스 개발 과정에 참여한다

생성형 AI와 코딩 에이전트는 코드 자동완성을 넘어 개발 작업의 일부를 직접 수행하는 단계로 발전하고 있다. 개발자는 AI로 코드 초안을 만들고 기존 코드를 설명받으며 테스트와 문서를 생성할 수 있다. 저장소의 이슈를 분석하고 여러 파일을 수정한 뒤 Pull Request 초안까지 만드는 도구도 늘고 있다.

![사람이 참여하는 개발 흐름과 AI가 참여하는 개발 흐름](/images/contents/it-trend/ai-oss/development-flow.png)

*그림 1. 사람이 참여하는 개발 흐름과 AI가 참여하는 개발 흐름*

중요한 변화는 AI가 사람을 완전히 대체한다는 데 있지 않다. 코드 작성에 쓰이던 사람의 시간이 설계 판단, 검증, 보안, 품질 관리로 이동한다는 점이 더 현실적인 변화다.

## 개발 진입장벽은 낮아지고 참여 범위는 넓어진다

AI는 새로운 개발자가 낯선 OSS 프로젝트를 이해하는 데 도움을 줄 수 있다. 복잡한 디렉터리 구조와 함수 간 관계를 설명하고, 수정 위치를 제안하기 때문이다. 문서가 부족한 프로젝트에서도 코드의 의미를 파악하는 시간이 줄어들 수 있다.

이는 소규모 프로젝트나 인력이 부족한 커뮤니티에 긍정적이다. 반복적인 문서 작성과 테스트 보완을 AI가 지원하면 메인테이너는 핵심 설계와 사용자 요구에 더 집중할 수 있다. 다만 기여의 양이 늘어나는 것과 프로젝트 품질이 높아지는 것은 별개의 문제다.

## 코드 생산이 늘어날수록 유지보수 부담도 커진다

AI가 생성한 코드는 문법적으로 자연스럽고 실행 가능해 보여도 프로젝트의 설계 원칙이나 장기 운영 조건을 충분히 반영하지 못할 수 있다. 불필요한 의존성, 중복 구현, 예외 처리 누락이 리뷰 단계에서 드러날 가능성도 있다.

특히 OSS에는 코드를 작성할 사람보다 변경을 검토할 메인테이너가 부족한 경우가 많다. Pull Request를 만드는 비용은 낮아졌지만 검토하고 병합 여부를 결정하는 비용은 여전히 사람에게 남는다. 앞으로 OSS의 병목은 코드 생성보다 빠르게 늘어나는 변경을 선별하고 검증하는 능력에서 발생할 가능성이 크다.

## 실제 사례가 보여주는 오픈소스의 명과 암

| 사례 | 보여주는 변화 | 기업 IT 관점의 의미 |
| :---- | :---- | :---- |
| PyTorch·Hugging Face | 공개 프레임워크와 모델 생태계가 AI 기술 확산을 가속 | 개별 모델뿐 아니라 플랫폼 지속성·호환성·커뮤니티를 함께 평가 |
| GitHub Copilot 등 코딩 AI | 반복 개발과 코드 초안 작성의 생산성 향상 | 개발 속도와 함께 리뷰 시간·결함률을 측정 |
| XZ Utils 백도어 사건 | 소수 메인테이너와 신뢰 관계에 의존한 공급망의 취약성 | 기여자 권한, 배포 절차, 빌드 산출물까지 추적 |
| Terraform·OpenTofu | 라이선스 변경이 새 커뮤니티 프로젝트 출범으로 연결 | 기술 적합성 외에 라이선스와 지배구조 변화 가능성 고려 |
| Redis·Valkey | 상용화 전략과 OSS 커뮤니티 이해관계의 충돌 | 제품명보다 실제 라이선스와 장기 운영 주체 확인 |
| OSI Open Source AI Definition | AI에서는 코드 공개만으로 개방성을 설명하기 어려움 | 모델·데이터 정보·수정 가능성까지 검토 범위 확대 |

XZ Utils 사건은 AI가 만든 사고는 아니다. 그러나 AI가 더 많은 코드와 기여를 만들어낼 때 기존 OSS의 구조적 취약성이 어떻게 확대될 수 있는지를 보여준다. Terraform과 Redis의 포크 사례 역시 OSS가 소스 코드뿐 아니라 라이선스, 운영 주체, 의사결정 구조로 형성되는 생태계임을 확인시킨다.

## AI가 만들었는가보다 어떻게 검증했는가가 중요해진다

AI가 OSS 구축에 기여하는 흐름 자체를 막기는 어렵다. 오히려 코드 작성, 테스트, 문서화에서 AI 활용은 자연스러운 개발 방식으로 자리 잡을 가능성이 높다. 문제는 AI가 코드를 작성했다는 사실 자체가 아니라, 그 결과가 어떤 절차를 거쳐 검증됐는가이다.

![AI 시대 OSS의 검증과 승인 흐름](/images/contents/it-trend/ai-oss/trust-structure.png)

*그림 2. AI 시대 OSS의 검증과 승인 흐름*

필자의 관점에서 앞으로 OSS 품질을 결정하는 핵심은 코드 생성 능력보다 검증 과정의 투명성이다. 어떤 변경이 AI에 의해 생성됐는지, 사람이 검토했는지, 테스트와 보안 검사를 통과했는지, 최종 승인 책임은 누구에게 있는지를 확인할 수 있어야 한다.

## 기업의 OSS 선택 기준도 달라져야 한다

기업은 지금까지 OSS를 도입할 때 기능, 성능, 커뮤니티 규모, 라이선스와 기술 지원 여부를 주로 확인했다. AI가 개발 과정에 들어오면서 이제는 프로젝트의 기여와 검증 체계도 함께 살펴봐야 한다.

| 기존 OSS 평가 기준 | AI 시대에 추가할 기준 |
| :---- | :---- |
| 기능과 성능 | AI 생성 코드의 표시 및 관리 정책 |
| 커뮤니티 규모 | 실제 리뷰에 참여하는 메인테이너 수 |
| 릴리스 주기 | 빌드·테스트·승인 과정의 추적 가능성 |
| 라이선스 | 코드·모델·데이터별 권리와 출처 |
| 취약점 이력 | 의존성 및 공급망 보안 관리 수준 |
| 기술 지원 | 프로젝트 지배구조와 장기 지속 가능성 |

Git 저장소의 소스 코드만 검토해서도 충분하지 않다. 실제 배포 패키지가 공개 저장소 코드와 동일하게 만들어졌는지, 어떤 의존성이 포함됐는지, 빌드와 배포 과정이 추적 가능한지도 확인해야 한다. SBOM, 서명된 패키지, 재현 가능한 빌드, 자동화된 취약점 점검의 중요성이 커지는 이유다.

## 미래의 OSS 경쟁력은 속도보다 신뢰에서 결정된다

앞으로 AI 에이전트는 버그 수정과 테스트 작성뿐 아니라 이슈 분류, 버전 업그레이드, 의존성 변경, 문서 갱신 같은 유지보수 작업에도 더 많이 참여할 것이다. 사람의 역할은 코드 작성자에서 설계자와 검증 책임자로 이동하고, 메인테이너의 운영 능력과 의사결정 구조가 기술 경쟁력의 일부가 될 가능성이 높다.

AI는 오픈소스를 더 빠르게 만들 수 있다. 그러나 더 안전하고 신뢰할 수 있게 만드는 문제까지 자동으로 해결하지는 않는다. 코드 생성 비용이 낮아질수록 검증, 책임, 추적성의 가치는 오히려 높아진다.

결국 AI 시대에 경쟁력 있는 OSS는 가장 많은 코드를 생산하는 프로젝트가 아닐 수 있다. 누가 기여했는지, 어떤 도구가 사용됐는지, 어떤 검증을 통과했는지, 문제가 발생했을 때 누가 대응하는지를 투명하게 설명할 수 있는 프로젝트가 기업과 개발자의 신뢰를 얻게 될 것이다.
