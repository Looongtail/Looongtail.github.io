AI 코딩은 빠르게 코드 자동 완성의 범위를 벗어나고 있다. 최근의 코딩 에이전트는 요구사항을 받은 뒤 코드베이스를 탐색하고, 여러 파일을 수정하며, 테스트를 실행하고, Pull Request 수준의 결과물까지 만들 수 있다. 여러 에이전트가 서로 다른 작업을 병렬로 수행하는 방식도 실제 개발 도구에 들어오고 있다.

이 변화에서 중요한 것은 AI가 얼마나 많은 코드를 생성할 수 있는가만이 아니다. 코드 작성의 상당 부분을 AI가 맡기 시작하면, 사람의 일은 무엇을 만들어야 하는지 정의하고, AI가 택한 설계가 적절한지 판단하며, 결과가 요구사항을 충족하는지 검증하는 쪽으로 이동한다.

1부에서 다룬 Whiteboard의 코드 연결 다이어그램, 구조 인지형 Diff, Decision Log도 이런 변화의 초기 모습으로 볼 수 있다. AI가 만든 코드를 한 줄씩 읽기 전에 전체 구조, 변경 의도, 주요 판단을 먼저 살피려는 접근이다. 그러나 AI가 만든 설명도 틀릴 수 있고, 보기 좋은 다이어그램이 올바른 구현을 보장하지도 않는다.

결국 AI와 함께하는 소프트웨어 개발의 경쟁은 코드 생성 능력 자체에서 **의도를 얼마나 명확하게 전달하고, 결과를 얼마나 독립적으로 검증하며, 그 과정을 조직의 지식으로 남길 수 있는가**로 옮겨가고 있다.

## 의도와 제약을 설계하는 사람의 역할

전통적인 개발에서 설계와 구현은 하나의 연속된 작업이었다. 개발자는 요구사항을 이해하고 구조를 설계한 뒤, 코드를 작성하며 세부 판단을 계속 조정했다. 구현 과정은 시스템을 이해하는 과정이기도 했다.

코딩 에이전트가 이 과정의 상당 부분을 수행하면 상황이 달라진다. 사람이 기능을 요청하면 에이전트는 바꿀 모듈, 활용할 라이브러리, 추가할 테스트 방식처럼 많은 세부 결정을 스스로 내릴 수 있다. 개발자는 코드 한 줄 한 줄을 만드는 사람이라기보다, 에이전트가 작업할 수 있는 환경과 조건을 정의하는 사람에 가까워진다.

OpenAI가 에이전트 중심 개발 환경을 설명하며 사용한 “Humans steer, agents execute”라는 표현은 이를 잘 보여 준다. 중요한 것은 일을 AI에 넘기는 행위가 아니라, 저장소 구조, 개발 규칙, 테스트, 도구, 피드백 루프를 통해 에이전트가 올바른 방향으로 일하도록 만드는 일이다. Anthropic의 대규모 Claude Code 세션 분석도 일반적인 세션에서 사람은 무엇을 할지에 관한 계획 결정을, 에이전트는 어떻게 할지에 관한 실행 결정을 더 많이 맡는 경향을 보고했다.

따라서 앞으로의 소프트웨어 설계는 사람에게 보여 주는 문서에만 머물기 어렵다. 요구사항, 인터페이스 계약, 데이터 구조, 성능 제약, 보안 정책은 에이전트도 해석하고 검증할 수 있는 형태여야 한다. 자연어 문서와 다이어그램에 더해 Schema, API Contract, Policy, Test처럼 기계가 실행하거나 검사할 수 있는 산출물의 중요성이 커질 수 있다.

AI 시대의 설계는 구현 전에 생각을 정리하는 과정인 동시에, **에이전트의 행동 범위와 결과 판단 기준을 정의하는 계약**이 된다.

## 변경 라인보다 의도와 영향 범위를 먼저 보는 리뷰

현재의 코드 리뷰는 대체로 Diff에서 출발한다. 추가·삭제된 코드를 읽고 구현 방식이나 예외 처리가 적절한지 확인한다. 사람이 작성한 비교적 작은 변경에는 효과적인 방법이다.

하지만 AI 에이전트는 짧은 시간에 더 넓은 변경을 생성한다. 기능 하나를 추가하면서 API, 데이터 모델, 서비스 로직, 테스트, 설정, 문서를 함께 바꾸는 일이 자연스러워진다. 여러 에이전트가 병렬로 일하면 사람이 읽을 수 있는 속도보다 검토 대상이 더 빨리 늘어날 수 있다.

이 환경에서는 모든 코드를 같은 깊이로 읽는 방식의 확장성이 떨어진다. 리뷰자가 먼저 물어야 할 질문은 “어떤 줄이 바뀌었는가”보다 **왜 바뀌었고 시스템의 어떤 동작이 달라지는가**다.

예를 들어 데이터 처리 로직이 바뀌었다면, 먼저 데이터 흐름이 어떻게 달라졌는지, 기존 인터페이스와 데이터 계약에 어떤 영향을 주는지, 실패가 어떤 경로로 전파될 수 있는지를 확인해야 한다. 그다음 위험도가 높은 실제 코드로 내려가는 순서가 현실적이다.

Whiteboard의 코드 연결 다이어그램과 Semantic Diff가 흥미로운 이유도 여기에 있다. 단지 코드를 보기 좋게 만드는 것이 아니라, 리뷰의 출발점을 소스 파일에서 시스템 구조와 변경 의도로 올리려는 시도이기 때문이다. 앞으로의 리뷰 인터페이스는 다음처럼 단계적으로 내려가는 형태가 될 가능성이 있다.

`Intent → Architecture → Change Impact → Code → Verification Evidence`

다만 이 순서는 코드를 생략한다는 뜻이 아니다. 위험도와 영향도를 파악해 사람이 어떤 코드에 집중할지를 돕는 탐색 순서다.

## 설명과 구현을 분리해 검증하는 증거

AI 기반 개발에서 특히 주의할 점은 설명과 검증을 혼동하지 않는 것이다. 코딩 에이전트에게 변경 내용을 설명해 달라고 하면 정돈된 요약, 아키텍처 다이어그램, 변경 이유를 만들 수 있다. 그러나 설명이 논리적으로 보인다는 사실과 실제 코드가 정확하다는 사실은 별개다.

AI가 구현에 잘못된 전제를 사용했다면 오류는 코드뿐 아니라 설명에도 함께 반영될 수 있다. 같은 모델이 같은 맥락에서 코드를 만들고 자신의 결과를 설명하면, 동일한 오류를 공유할 위험도 있다. AI 리뷰어를 하나 더 둔다고 자동으로 해결되는 것도 아니다. 모델, Context, 판단 기준이 유사하다면 같은 문제를 놓칠 수 있다.

따라서 중요한 것은 더 그럴듯한 설명이 아니라 **설명과 실제 구현을 독립적으로 대조할 수 있는 검증 경로**다. AST와 의존성 그래프로 실제 호출 관계를 확인하고, 정적 분석으로 보안·타입·데이터 흐름 문제를 찾고, 테스트 실행으로 요구 동작을 확인하는 방식이 여기에 해당한다. API Contract나 Schema 변경 비교, 성능 시험, 보안 정책 검사도 증거로 연결할 수 있다.

AI는 이런 증거를 수집하고 이해하기 쉽게 설명하는 데 유용할 수 있다. 하지만 최종 판단의 근거는 AI의 자신감 있는 서술보다 코드에서 추출한 구조, 재현 가능한 테스트 결과, 정적 분석 결과에 두는 편이 바람직하다. 코드 리뷰 이해 자체가 여러 추론 단계를 요구한다는 점은 CodeReviewQA 연구가 변경 유형 인식, 변경 위치 파악, 해결책 식별을 별도로 평가한 데서도 확인할 수 있다.

## 요구사항부터 운영까지 이어지는 추적성

소프트웨어 엔지니어링에서 Traceability는 새 개념이 아니다. 요구사항이 어떤 설계 요소와 연결되고, 어떤 코드와 테스트로 구현됐는지를 추적하는 일은 오래전부터 중요했다. 다만 유지 비용 때문에 실제 현장에서는 제한적으로 운영되는 경우가 많았다.

AI 에이전트가 대규모 변경을 반복 생성하면 이 관계를 다시 중요하게 만들어 준다. 사람이 직접 코드를 쓸 때는 요구사항과 구현의 관계가 작성자의 머릿속에 어느 정도 남는다. 반면 여러 에이전트가 API, 데이터 처리, 테스트를 나눠 구현하면, 몇 달 뒤 요구사항이 바뀌었을 때 무엇을 다시 확인해야 하는지가 빠르게 불분명해질 수 있다.

개발 플랫폼이 다음 연결 관계를 기본 정보로 관리한다면 영향 분석의 출발점이 생긴다.

`Requirement → Design Decision → Architecture Component → Source Code → Test → Deployment → Runtime Telemetry`

이 관계가 유지되면 개발자는 요구사항 하나에서 관련 구현과 테스트를 찾을 수 있고, 코드 변경에서 영향을 받을 기능을 역으로 탐색할 수도 있다. Whiteboard가 다이어그램과 코드를 연결하고 Decision Log를 보여 주는 것은 이 방향의 초기 단계로 해석할 수 있다.

다음 단계는 화면의 링크를 넘어서 산출물 사이의 관계를 유지하는 Traceability Layer다. 이 체계의 가치는 AI를 통제하는 데만 있지 않다. 신규 개발자의 온보딩, 장애 분석, 아키텍처 리뷰, 변경 영향 분석을 위한 공통 기반이 될 수 있다.

## 관계를 갖는 Engineering Knowledge의 필요성

코딩 에이전트의 성과는 모델 능력만큼 어떤 Context를 받는가에 좌우된다. 새 에이전트가 저장소에 들어왔을 때, 코드만 읽고 모든 설계 의도를 복원하기는 어렵다. 특정 데이터 모델을 택한 이유, 직접 호출하면 안 되는 서비스, 과거 호환성 때문에 유지하는 API는 코드만으로 충분히 드러나지 않을 수 있다.

이 지식이 Wiki, Issue, ADR, Pull Request, 담당자의 기억에 흩어져 있으면 AI도 사람과 같은 문제를 겪는다. OpenAI의 사례가 저장소 안에서 발견할 수 없는 문서와 대화 기록은 에이전트의 맥락이 되기 어렵다고 지적한 이유다.

그래서 AI 시대의 개발 지식 관리는 문서 검색만으로 충분하지 않을 수 있다. 시스템 구성 요소, 인터페이스, 요구사항, 설계 결정, 코드, 테스트 사이의 관계를 구조화한 **Engineering Knowledge Layer**가 필요해질 가능성이 있다. 여기에 ADR, API·Schema 정보, Service Catalog, 코드 의존성, Issue·Requirement, 테스트와 배포 이력이 연결될 수 있다.

핵심은 거대한 지식 그래프를 만드는 일이 아니다. 에이전트가 “이 모듈을 바꾸면 어떤 계약과 설계 결정의 영향을 받는가”를 찾고, 리뷰어가 “이번 변경이 기존 아키텍처 원칙과 충돌하는가”를 확인할 수 있어야 한다. 이렇게 축적된 지식은 AI뿐 아니라 사람의 온보딩과 운영에도 쓰이는 장기 자산이다.

## 역할 분담보다 독립된 검증 경로를 갖는 멀티 에이전트

에이전트 기술이 발전하며 구현 Agent, Test Agent, Review Agent, Security Agent처럼 역할을 나누는 구조가 늘고 있다. 그러나 에이전트 수가 많아진다고 결과의 신뢰도가 자동으로 높아지지는 않는다. 같은 모델, 같은 정보, 같은 판단 기준을 쓰면 같은 오류를 반복할 수 있다.

중요한 것은 에이전트의 수보다 **각 역할이 서로 다른 검증 기준과 도구를 갖는가**다. 구현 에이전트는 요구사항을 바탕으로 코드를 작성하고, 리뷰 에이전트는 변경 영향과 설계 원칙을 살피며, 테스트 에이전트는 실행 결과를 확인할 수 있다. 보안 에이전트는 SAST나 의존성 스캐너를, 아키텍처 에이전트는 서비스 의존성과 API Contract 검사를 활용할 수 있다.

즉 멀티 에이전트의 핵심은 여러 AI의 의견을 투표하는 데 있지 않다. 서로 다른 Evidence를 수집하도록 역할과 도구를 설계하는 데 있다. 인간 리뷰어에게도 긴 대화 기록보다 요구사항 충족 여부, 아키텍처 변화, 통과한 검증, 남은 위험이 구조적으로 제시되는 편이 더 유용하다.

## 에이전트를 통제하는 개발 플랫폼

AI 코딩이 조직 전체로 퍼지면 개인 IDE만의 문제가 아니다. 에이전트가 접근할 수 있는 저장소와 디렉터리, 실행할 수 있는 명령, 외부 시스템 접근, 배포 가능한 변경을 조직 차원에서 관리해야 한다.

최근 코딩 에이전트 제품이 저장소 규칙, Agent Skill, MCP, Issue Tracker, Service Catalog, CI/CD와 연결되는 방향으로 발전하는 것도 이와 관련 있다. 예를 들어 GitHub는 코드 리뷰가 저장소의 Skill과 MCP 서버를 통해 팀의 도구·표준·외부 Context를 읽기 전용으로 활용할 수 있도록 제공한다. 에이전트는 단순 코드 생성 모델이 아니라 개발 환경에서 행동하는 실행 주체가 되고 있다.

기업의 Internal Developer Platform도 이런 변화를 받아들여야 한다. 기존 플랫폼이 개발자에게 표준 Pipeline, 배포 환경, Observability, Security 기능을 제공했다면, 앞으로는 AI 에이전트에도 같은 Guardrail을 제공해야 한다. 변경 가능한 경로를 제한하고, 중요한 API나 데이터 모델 변경에는 추가 검증을 요구하며, 프로덕션과 연결되는 변경은 사람이 승인하도록 구성하는 식이다.

AI 시대의 Developer Platform은 에이전트에 무제한의 자유를 주는 플랫폼이 아니라, 빠르게 작업하면서도 조직의 아키텍처와 품질 기준을 벗어나지 않게 하는 **Harness**에 가깝다.

## 신뢰할 수 있는 변경을 측정하는 생산성

AI 코딩의 생산성을 평가할 때 가장 쉬운 지표는 코드 생성 속도다. 하지만 실제 개발 비용에는 요구사항 분석, 리뷰, 테스트, 장애 대응, 유지보수가 모두 포함된다.

연구 결과도 하나의 단순한 결론으로 정리되지 않는다. METR의 2025년 무작위 대조 연구는 익숙한 대형 오픈소스 저장소에서 일하는 숙련 개발자라는 특정 조건에서 당시 AI 도구 사용이 작업 완료 시간을 늘렸다고 보고했다. METR은 2026년 후속 설명에서 그 연구 설계와 당시 도구의 한계를 짚으며, 결과를 현재와 미래의 모든 개발 작업으로 일반화할 수 없다고 밝혔다. 반면 DORA는 AI가 초기 생성 작업의 마찰을 줄이지만, 절감한 시간이 감사·검증 비용으로 다시 배분될 수 있음을 관찰했다.

따라서 기업은 AI 도입 효과를 코드 생성량이나 에이전트 사용 횟수로만 판단해서는 안 된다. Lead Time, Review Time, Change Failure Rate, Defect Escape Rate, Rework, 테스트 커버리지처럼 SDLC 전체 지표와 함께 봐야 한다.

AI 시대의 생산성은 얼마나 많은 코드를 AI가 만들었는가보다, **얼마나 많은 변경을 사람이 신뢰하고 운영 환경에 전달할 수 있는가**에 가깝다.

## 의도와 증거를 중심으로 재구성되는 개발 인터페이스

코드가 사라지지는 않는다. 소프트웨어는 코드로 실행되며 중요한 문제를 해결하려면 개발자가 실제 구현을 이해할 수 있어야 한다. AI가 모든 코드를 쓰고 사람은 다이어그램만 보는 미래를 전제하는 것은 지나친 단순화다.

다만 사람이 모든 변경의 모든 코드를 같은 깊이로 읽어야 한다는 전제는 약해질 수 있다. AI가 대량의 구현을 맡는다면 사람은 요구사항과 설계 의도를 검토하고, 아키텍처 변화와 위험 영역을 확인하고, 테스트·정적 분석 같은 검증 증거를 살핀 뒤 필요할 때 코드로 내려가는 방식을 택할 가능성이 높다.

개발 인터페이스의 변화는 다음처럼 요약할 수 있다.

**Code-centric Development**

`Requirement → Developer → Code → Diff → Review`

**Agentic Development**

`Intent → Agent → Design/Code → Verification Evidence → Human Review`

![코드 중심 개발과 에이전트 중심 개발에서 검토가 시작되는 위치를 비교한 흐름도](/images/contents/it-trend/whiteboard/agentic-development-flow.svg)

*그림 1. 코드 중심 개발은 구현과 Diff에서, 에이전트 중심 개발은 의도와 검증 증거에서 검토를 시작하는 흐름을 보여 준다. 이 글의 분석을 바탕으로 구성한 도식.*

Whiteboard는 이 변화의 완성형이라기보다 초기 신호다. 다이어그램과 코드의 연결, Semantic Diff, Decision Log는 AI가 만든 결과를 사람이 더 높은 추상화 수준에서 이해하려는 시도다. 여기에 요구사항 추적, 정적 분석, 테스트 증거, 런타임 텔레메트리, 개발 지식이 연결되면 단순한 AI 코딩 UI를 넘어 새로운 소프트웨어 엔지니어링 Control Plane에 가까워질 수 있다.

기업 IT가 주목할 지점도 여기에 있다. 경쟁력은 가장 강력한 코딩 에이전트를 먼저 도입하는 데서만 나오지 않는다. 에이전트에 조직의 개발 원칙과 시스템 맥락을 전달하고, 생성된 결과를 독립적으로 검증하며, 그 과정의 지식을 다음 개발에 다시 활용하는 체계를 만드는 일이 더 중요하다.

AI가 더 많은 코드를 작성하는 시대에도 최종 책임은 사라지지 않는다. 오히려 구현 속도가 빨라질수록 **무엇을 만들지 명확하게 정의하고, 무엇이 바뀌었는지 이해하며, 그것이 올바르다는 증거를 확보하는 능력**이 개발 조직의 핵심 역량이 된다.
