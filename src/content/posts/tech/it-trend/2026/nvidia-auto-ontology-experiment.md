시맨틱 레이어는 기업 데이터 서비스에서 지표의 일관성을 유지하는 데 쓰여 왔다. 예를 들어 월 매출을 보고서마다 따로 정의하면 주문일과 송장일 중 어떤 날짜를 쓰는지, 반품을 어느 달에 반영하는지에 따라 숫자가 달라진다. 계산식과 기준을 한곳에 정의하고 여러 보고서가 이를 재사용하면 지표가 달라지는 원인을 줄이고, 기준 변경도 한곳에서 관리할 수 있다.

Power BI는 공유 시맨틱 모델을 기반으로 여러 보고서를 만들 수 있게 하고, dbt는 한곳에 정의한 지표를 여러 분석 도구에서 조회할 수 있게 한다. AI 에이전트가 데이터를 사용하는 경우에도 같은 원리가 적용된다. 에이전트가 기존 보고서와 같은 매출 기준을 쓰려면 계산식과 기준 날짜, 지역을 판별하는 조인 경로를 참조할 수 있어야 한다.

NVIDIA는 이런 시맨틱 모델의 구성을 돕는 **Auto Ontology**를 Apache 2.0 라이선스의 오픈소스로 공개했다. 데이터베이스의 구조와 사용 이력에서 업무 용어와 관계의 후보를 만들어 검토의 출발점을 제공한다. 이 글에서는 Microsoft Wide World Importers 공개 샘플로 어떤 정의까지 자동으로 만들 수 있는지 확인하고, 현업이 어떤 기준을 추가하고 검증해야 하는지 살펴본다.

## NVIDIA Auto Ontology가 생성하는 의미 모델의 초안

Auto Ontology는 데이터베이스의 테이블, 컬럼, 키, 샘플값을 읽어 ‘고객’, ‘송장’, ‘배송 도시’ 같은 업무 개념을 실제 데이터에 연결한다. 이렇게 개념과 관계를 구조화한 모델이 온톨로지다. SQL 이력을 제공하면 재사용할 계산식도 제안할 수 있다.

웹 화면에서 생성된 용어와 컬럼 매핑을 검토하고, 그래프로 관계를 확인할 수 있다. 검증한 정의를 승인하면 에이전트가 참조할 업무 모델을 관리할 수 있다. 기업 입장에서는 데이터 카탈로그와 BI에 흩어진 정의를 연결할 초안을 얻는 데 의미가 있다.

## 업무 맥락을 재사용 가능한 정의로 만드는 시맨틱 레이어

**시맨틱 레이어**에는 업무 용어, 지표, 관계를 실제 데이터에 연결해 여러 도구가 재사용할 수 있도록 담는다. 이 정의는 AI가 데이터를 해석할 때 참조하는 업무 맥락이기도 하다. 가령 ‘지역은 배송지 기준’이라는 규칙을 배송 도시 컬럼과 조인 경로에 연결하면, 같은 모델이 규칙의 설명과 실행에 필요한 정보를 함께 제공한다. 규칙을 검토할 때는 업무 규정과 기존 리포트를 근거로 삼을 수 있다.

| 구성 요소 | 담는 내용 | 업무에서 확인할 항목 |
| :--- | :--- | :--- |
| Term | 고객, 송장 같은 업무 개념과 동의어 | 청구 고객과 배송 고객을 구분하는가 |
| Column Attribute | 업무 개념에 연결된 컬럼과 그 의미 | 날짜가 주문일인지 송장일인지 드러나는가 |
| SQL Attribute | 여러 질문에 재사용할 SQL 계산식 | 매출 계산에 송장 금액을 쓰는가 |
| Relationship | 테이블 사이의 조인 관계 | 지역 집계에서 배송 도시를 거치는가 |

## 자동 생성 범위와 화면별 검토 방법

로컬 PostgreSQL에 약 226만 행의 공개 샘플을 두고 NVIDIA 호스팅 모델을 연결했다. Auto Ontology는 5개 스키마에서 테이블 51개와 컬럼 589개를 카탈로그에 기록했다. 약 17분이 걸린 의미 모델 생성 단계에서는 용어 51개, 컬럼 속성 479개, 의미 모델에 반영된 키 관계 85개가 나왔다. 쿼리 이력을 제공하지 않은 이 실험에서는 재사용할 SQL 계산식과 브리지 테이블 속성이 생성되지 않았다.

**Discovery에서 업무 용어의 데이터 근거 확인하기.** `Customer`를 검색하면 관련 용어와 테이블·뷰·컬럼이 한 화면에 나온다. 이 실험에서는 총 92건이 검색됐다. 이 목록을 기존 고객 용어 사전과 대조하면 여러 테이블에 흩어진 고객 역할 가운데 어떤 것을 표준 정의에 연결할지 검토할 수 있다.

**Exploration에서 관계 따라가기.** 그래프에서는 고객, 주문, 송장, 도시가 어떻게 이어지는지 확인할 수 있다. 송장과 지역 정보가 사람 테이블을 거쳐 연결된다면, 각 키가 담당자나 수정자를 가리키는지 확인할 계기가 된다. 물리 데이터 객체 보기로 전환하면 조인의 근거가 되는 테이블과 컬럼을 살펴볼 수 있다.

## 질의로 드러난 지표와 관계 정의의 공백

초안에 있는 정보만으로 송장·배송지 기준을 적용할 수 있는지 살펴보기 위해 공식 예제 질문을 한국어로 옮겨 **Chat**에서 실행했다.

> 2015년 6월 펜실베이니아에서 판매된 USB food flash drive - sushi roll의 매출은 얼마인가?

결과 카드에 표시된 값은 **4,544**였다. 생성 SQL에는 제품과 날짜 조건이 들어 있었지만 펜실베이니아 조건이 빠졌다. 설명에도 유효한 조인 경로를 찾지 못해 주 필터를 생략했다고 적혀 있었다. 결과는 해당 제품의 2015년 6월 주문 금액을 지역 제한 없이 합산한 값이었다. 숫자만 보고 지나갔다면 지역 매출로 읽기 쉬운 화면이었다.

![한국어 질문과 지역 필터가 빠진 SQL, 실행값 4,544가 표시된 결과 화면](/images/contents/it-trend/auto-ontology/usage-07-korean-question-result.jpg)

*그림 4. 결과의 SQL을 보면 제품·기간은 적용됐고 배송지 기준 지역 조건은 빠져 있다.*

API 호출과 영문 질문에서도 서로 다른 계산식과 조인이 선택됐다. 마지막 행은 송장과 배송지를 기준으로 직접 실행한 비교값이다.

| 실행 | SQL이 적용한 기준 | 관찰 결과 |
| :--- | :--- | :--- |
| 한국어 Chat | 주문 수량×단가, 지역 제한 없음 | 4,544 |
| 같은 한국어 문장의 대화 ID 없는 API 호출 | 주문 수량×단가, 고객의 우편 도시로 주 필터 적용 | 512.0 |
| 공식 예제의 영문 질문을 로컬에서 실행 | 송장 연락 담당자와 주 레코드의 최종 수정자를 사람 테이블로 연결 | 매출 값이 비어 있음 |
| 직접 작성한 기준 SQL | 송장 → 고객 → 배송 도시 → 주 | $588.80, 송장 항목 3건 |

영문 질의에 사용된 두 외래 키는 원본 DB에 실제로 있었다. 그 관계가 나타내는 것은 송장의 연락 담당자와 주 정보의 최종 수정자다. 배송 지역과는 무관하다. 반대로 송장·배송지 기준에 필요한 `customers.deliverycityid → cities.cityid` 역시 원본 DB에 있었지만, 실험에서 생성된 의미 관계 85개에는 포함되지 않았다. 조인이 실행된다는 사실만으로 업무적으로 올바른 관계를 선택했는지 확인하기 어려운 이유다.

원본 샘플에는 주문과 송장, 우편지와 배송지가 모두 있었다. 이 실험에서는 어느 조합이 공식 매출인지 승인한 정의를 추가하지 않았다. 언어와 호출 경로가 함께 달랐으므로 한국어 자체의 영향을 판단하기는 어렵다. 배송지 관계를 보완하고 지표를 승인한 뒤의 정확도는 후속 검증 범위다.

## 시맨틱 레이어를 구성하기 위해 먼저 준비할 정보

영업 도메인에서 시작한다면 아래 항목을 기준으로 자료를 모을 수 있다. 오른쪽 열은 자료를 검토한 뒤 의미 모델이나 검증 자료에 어떤 형태로 남길지 보여준다.

| 준비할 정보 | 근거가 되는 자료 | 모델이나 검증 자료에 남길 내용 |
| :--- | :--- | :--- |
| 업무 용어와 역할 | 용어 사전, 업무 매뉴얼, 담당자 확인 | 주문 고객과 배송 고객처럼 역할이 다른 용어, 동의어, 실제 컬럼 |
| 지표와 집계 단위 | 공식 BI 리포트, 지표 사전, 검증된 SQL | 계산식, 한 행의 기준, 기준 날짜, 취소·반품 처리, 허용 집계 수준 |
| 관계와 조인 조건 | ERD, 키 제약, 실제 값의 분포, 기존 조인 SQL | 배송지와 우편지의 구분, 조인 키, 관계의 카디널리티와 중복 집계 가능성 |
| 데이터 사용 범위 | 데이터 카탈로그, 접근 정책, 도메인 담당자 | 공식 데이터 원천, 허용 범위, 민감 컬럼, 담당자와 승인 이력 |
| 동작을 확인할 사례 | 기존 리포트 결과, 대표 질문, 경계 사례 | 기준 SQL과 예상값, 조건이 모호하거나 데이터가 부족할 때의 처리 |

예를 들어 ‘지역별 송장 매출’ 한 항목에 송장 라인 단위, 적용할 금액과 기준 날짜, 고객에서 배송 도시와 주로 이어지는 관계를 함께 명시한다. 한 고객에 여러 주소가 연결될 수 있다면 조인 시 매출이 중복 합산되는지도 확인한다. 지표와 조인마다 참조한 리포트나 SQL, 승인 책임자와 개정 이력을 남기면 스키마가 바뀌었을 때 재검토할 대상을 찾을 수 있다. 이는 기업 파일럿의 정보 설계 예시이며 각 관리 항목이 Auto Ontology에서 자동 생성되는 것은 아니다.

## 활용 가능성 — 기존 업무 정의를 연결하는 모델링 도구

판매 데이터 마트처럼 업무 범위와 담당자가 분명한 영역부터 시작할 수 있다. 자동으로 생성한 컬럼 설명과 관계 후보를 기존 BI 정의와 대조하면, 데이터 카탈로그의 업무 용어를 실제 지표와 조인에 연결하는 작업에 활용할 수 있다. 이번 실험에서는 이런 후보를 생성하고 화면에서 검토할 수 있음을 확인했다. 기존 문서화 방식 대비 검토 시간은 측정하지 않았다.

1. **기준 답변 준비.** 공식 리포트에서 확인할 수 있는 대표 질문에 기준 SQL과 예상값을 붙인다. 한국어 표현 변형, 주소 역할이 모호한 질문, 값이 없거나 권한이 제한된 질문도 포함한다.
2. **검토와 승인.** 데이터 모델러가 용어와 조인 경로를 검토하고 업무 담당자가 지표를 승인한다. 같은 모델에서 스키마만 썼을 때, 자동 생성한 의미 모델을 썼을 때, 사람이 승인한 모델을 썼을 때를 비교한다. NVIDIA 평가 도구는 앞의 두 구성을 비교하는 출발점을 제공한다.
3. **사용 범위 결정.** 실행 결과가 공식 BI와 일치하는지, 필수 조건을 보존하는지, 근거가 부족할 때 확인을 요청하거나 답변을 보류하는지 평가한다. 재무 결산이나 대외 보고처럼 오류의 영향이 큰 용도라면 이런 조건을 먼저 확인한다. 스키마나 모델이 바뀌면 대표 질문과 주요 조인 경로를 다시 검증한다.

## 한계 — 자동 생성의 정확도와 운영 조건

스키마의 키는 데이터가 어떻게 연결되는지 알려주지만, 업무에서 어떤 연결을 선택해야 하는지는 별도의 판단이 필요하다. 샘플에서도 실제 외래 키를 따라간 SQL이 지역 매출에 맞지 않았고, 지역 조건을 생략한 실행값이 반환됐다. 자동 생성 결과를 공식 지표나 보고에 사용하려면 계산 기준과 필수 조건을 승인하고, 기준 SQL과 대조하는 절차가 필요하다.

공식 문서는 PostgreSQL, MySQL, Databricks, Snowflake, ClickHouse, Trino, Apache Kyuubi, HeavyDB, DuckDB, SQLite 연결을 안내한다. 실험에서 사용한 엔진은 PostgreSQL이다. Trino를 통해 Impala–Kudu 데이터를 조회하는 조직이라면, 해당 데이터가 Trino에 테이블로 노출되고 Auto Ontology 계정으로 스키마 조회와 읽기 실행이 가능한지부터 확인할 수 있다. 실제 연결 조합에서는 타입, 식별자 대소문자, 샘플링, 조인 SQL과 원본 시스템에 전달되는 쿼리 범위까지 시험해야 한다.

모델 호환성은 도입 비용에 직접 영향을 준다. 이번 호스팅 모델 조합에서는 일괄 임베딩 요청과 구조화 출력이 실패했다. 요청 규모를 줄이고 모델 호출 방식을 바꾼 뒤 생성을 마쳤다. 사내 모델로 운영한다면 각 역할의 API 호환성과 생성 시간, 질의 지연, 처리량을 실제 데이터 범위와 예상 동시 사용자 수에 맞춰 검증해야 한다. NVIDIA NIM은 자체 인프라에서 모델 API를 제공하는 선택지다.

웹 화면에서 검토한 의미 모델은 API와 읽기 전용 MCP 도구를 통해 에이전트에 제공할 수 있다. 이번 실험은 웹 UI와 백엔드 질의까지 확인했다. MCP를 적용할 경우에는 호출자의 권한이 원본 데이터의 행·컬럼 접근 범위에 어떻게 반영되는지 검증해야 한다. 의미 모델을 다른 도구로 옮길 때는 Apache Ossie YAML로 교환할 수 있는 정의와 대상 도구에서의 계산 결과를 함께 대조할 필요가 있다.

호스팅 모델을 쓰면 호출 단계와 설정에 따라 테이블·컬럼 이름, 제한된 샘플값, 질문과 검색 문맥이 외부 엔드포인트에 전달될 수 있다. 회사 DB에 직접 연결할 수 없는 개발 환경이라면, 공개 데이터나 반출 승인을 받은 합성 샘플에 주문·송장과 우편지·배송지처럼 구분할 역할을 남겨두고 UI와 관계 생성 흐름을 먼저 시험할 수 있다. 실제 데이터에 대한 인증은 내부 환경에서 진행한다. 차단망에서는 앱의 컨테이너와 패키지 외에 내부에서 호출 가능한 모델 서비스, 모델 반입과 업데이트 절차, 처리량과 장애 대응 체계까지 준비해야 한다.

연결 자격 증명 관리도 배포의 일부다. 공식 문서에 따르면 Vault를 구성하지 않으면 UI에서 등록한 연결의 자격 증명이 메타데이터 PostgreSQL에 평문으로 저장된다. 백엔드와 수집 서비스는 사설 네트워크에 두고, 운영 DB에는 허용된 뷰만 읽는 최소 권한 계정을 사용하는 구성이 적절하다. 사용자별 접근 범위, 쿼리 시간과 결과 행 수 제한, 감사 기록, 메타데이터와 샘플의 외부 전송 범위는 파일럿 단계부터 확인할 항목이다.

## 바라는 점 — 검증 근거와 변경 이력을 잇는 운영 흐름

기존 BI의 지표 사전과 검증된 SQL을 가져와 자동 생성 후보와 나란히 검토할 수 있으면 좋겠다. 예를 들어 ‘지역별 송장 매출’을 검토하는 화면에서 계산식과 배송 도시 조인, 그 기준을 사용한 공식 보고서를 함께 확인할 수 있다면, 담당자가 어떤 정의를 승인했는지 설명하기 쉬워진다.

스키마를 다시 수집할 때는 기존 승인본과 새 후보 사이의 차이를 보여주고, 영향을 받는 지표와 검증 사례를 함께 표시하는 흐름을 기대한다. 배송지 조인처럼 집계 범위를 바꾸는 관계가 달라졌다면 담당자가 차이를 검토하고, 기준 결과를 다시 확인한 뒤 승인할 수 있다. 필수 날짜나 지역 조건을 적용할 수 없는 경우에는 어떤 정의나 관계가 부족한지 드러내는 응답도 현업 검토에 도움이 된다.
