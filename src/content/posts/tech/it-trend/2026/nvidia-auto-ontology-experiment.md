“지난달 펜실베이니아에서 이 제품이 얼마나 팔렸나요?”라는 질문에 답하려면 먼저 매출의 기준을 정해야 한다. 주문을 받은 금액과 송장을 발행한 금액은 다를 수 있다. 고객의 우편 주소와 배송 주소가 서로 다른 주에 있다면 어느 쪽을 지역 매출로 잡느냐에 따라 숫자가 바뀐다. SQL을 작성하기 전에 현업이 합의해야 할 내용이다.

NVIDIA가 공개한 오픈소스 프로젝트 Auto Ontology는 데이터베이스에서 이런 업무 용어와 관계의 초안을 만들고, 사람이 검토한 정의를 AI의 자연어 질의에 활용할 수 있게 한다. 실제로 어디까지 자동화되는지 살펴보기 위해 로컬 PC에 설치한 뒤 Microsoft Wide World Importers 공개 샘플을 연결했다. 메타데이터를 수집하고 웹 화면에서 관계를 탐색한 다음, 지역별 제품 매출을 직접 물었다.

## 데이터베이스 구조를 업무 언어로 바꾸는 의미 계층

데이터 카탈로그에서 `Customers`와 `Cities` 테이블을 찾을 수 있어도, 지역 매출을 계산할 때 어떤 주소를 써야 하는지는 따로 정해야 한다. Auto Ontology가 만드는 의미 계층은 이런 업무 용어를 실제 컬럼, 계산식, 조인 경로에 연결한다. 프로젝트에서 말하는 온톨로지는 이 정의와 관계를 그래프로 표현한 모델이다.

| 구성 요소 | 담는 내용 | 업무에서 확인할 항목 |
| :--- | :--- | :--- |
| Term | 고객, 송장 같은 업무 개념과 동의어 | 청구 고객과 배송 고객을 구분하는가 |
| SQL Attribute | 여러 질문에 재사용할 SQL 계산식 | 매출 계산에 송장 금액을 쓰는가 |
| Relationship | 테이블 사이의 조인 관계 | 지역 집계에서 배송 도시를 거치는가 |

사용 흐름은 생성, 인증, 질의로 이어진다. 수집 서비스가 테이블·컬럼·키와 제한된 샘플값을 바탕으로 초안을 만든다. 쿼리 이력을 제공하면 반복해서 쓰는 계산식도 후보로 제안할 수 있다. 데이터 담당자는 설명과 정의를 검토하고, 대표 질문을 실행해 SQL과 결과를 비교한 뒤 검증한 정의를 승인한다. 이후 에이전트는 질문과 관련된 정의를 검색하고 의미 계층에 등록된 관계를 바탕으로 SQL을 작성한다. 질문 의도를 분류하고 SQL을 생성·검사하는 과정에는 모델이 관여한다.

## 소스 연결부터 생성 결과를 검토하는 과정

실험에서는 Apple Silicon PC에 Docker Compose로 웹 UI, 백엔드, 수집 서비스, PostgreSQL·pgvector를 띄웠다. 평가 저장소의 적재 스크립트로 약 226만 행의 Wide World Importers 데이터를 로컬 PostgreSQL에 넣었다. 앱과 샘플 DB는 로컬에 뒀고, 모델 추론에는 NVIDIA 호스팅 API를 사용했다. 웹 화면에서 시작한다면 **Settings → Connections**에서 소스 DB를 등록하고, **Settings → Semantic Compilation**에서 의미 모델 생성을 켜는 순서다.

5개 스키마의 51개 테이블과 589개 컬럼을 카탈로그에 기록하는 데 약 2.6초가 걸렸다. 모델 인증 정보가 없던 첫 시도에서는 구조가 수집된 뒤에도 임베딩 요청이 실패해 웹 화면에 `Semantic Layer Not Ready`가 표시됐다. 테이블 목록이 보이는 상태와 업무 용어를 검색하고 질의할 수 있는 상태를 구분할 수 있는 장면이었다.

모델 연결을 조정한 뒤 의미 모델 생성에는 약 17분이 걸렸다. 용어 51개, 컬럼 속성 479개, 의미 관계를 나타내는 외래 키 85개, 검색용 벡터 530개가 만들어졌다. 이번에는 쿼리 이력을 넣지 않았고 SQL Attribute와 브리지 테이블 속성은 생성되지 않았다. 아래 화면에서 확인한 것은 이 자동 생성 상태의 모델이다.

**Discovery에서 데이터 찾기.** `Customer`를 검색하면 업무 용어와 관련 테이블·뷰·컬럼이 한 화면에 나온다. 이 실험에서는 총 92건이 검색됐다. 낯선 시스템을 인수받은 분석가라면 고객을 다루는 데이터가 어디에 흩어져 있는지 파악하는 데 쓸 수 있다.

![Discovery에서 Customer를 검색해 업무 용어와 관련 데이터 객체를 찾은 화면](/images/contents/it-trend/auto-ontology/usage-01-discovery-search.jpg)

*그림 1. 같은 업무 용어로 개념과 물리 데이터 객체를 함께 찾을 수 있는 Discovery 화면.*

**Term 상세에서 정의 검토하기.** 검색 결과에서 `Customer`를 열면 자동 생성한 설명, 연결된 엔터티와 컬럼 속성을 볼 수 있다. `Pending Approval` 상태의 항목을 검토하면서, 예를 들어 고객의 우편지와 배송지를 어디에 쓰는지 구체적으로 적을 수 있다.

**Exploration에서 관계 따라가기.** 그래프에서는 고객, 주문, 송장, 도시가 어떻게 이어지는지 확인할 수 있다. 송장과 지역 정보가 사람 테이블을 거쳐 연결된다면, 각 키가 담당자나 수정자를 가리키는지 확인할 계기가 된다. 물리 데이터 객체 보기로 전환하면 조인의 근거가 되는 테이블과 컬럼을 살펴볼 수 있다.

## 한국어 질문에서 확인한 필수 조건 누락

마지막으로 **Chat**에서 공식 예제 질문을 한국어로 옮겨 입력했다. 제품명은 원본 DB에 적힌 문자열을 그대로 썼다.

> 2015년 6월 펜실베이니아에서 판매된 USB food flash drive - sushi roll의 매출은 얼마인가?

![Chat 입력창에 한국어 매출 질문을 작성한 화면](/images/contents/it-trend/auto-ontology/usage-05-korean-question-ready.jpg)

*그림 4. 제품명은 원본 데이터에 맞추고 기간, 지역, 지표는 한국어로 입력했다.*

질문을 전송하자 에이전트는 의도 분류를 시작했고 SQL 생성과 실행까지 진행했다. 결과 화면에는 실행값과 함께 영어 설명과 생성 SQL이 나타났다.

![한국어 질문을 전송한 뒤 에이전트가 질문을 분류하는 화면](/images/contents/it-trend/auto-ontology/usage-06-korean-question-processing.jpg)

*그림 5. 질문이 접수된 뒤 Chat에서 분류 단계를 확인할 수 있다.*

결과 카드에 표시된 값은 **4,544**였다. 생성 SQL에는 제품과 날짜 조건이 들어 있었지만 펜실베이니아 조건이 빠졌다. 설명에도 유효한 조인 경로를 찾지 못해 주 필터를 생략했다고 적혀 있었다. 결과는 해당 제품의 2015년 6월 주문 금액을 지역 제한 없이 합산한 값이었다. 숫자만 보고 지나갔다면 지역 매출로 읽기 쉬운 화면이었다.

![한국어 질문과 지역 필터가 빠진 SQL, 실행값 4,544가 표시된 결과 화면](/images/contents/it-trend/auto-ontology/usage-07-korean-question-result.jpg)

*그림 6. 제품명과 기간이 SQL에 들어갔지만 Pennsylvania 조건이 생략된 실행 결과.*

영문 예제와 별도의 API 호출을 비교하니 실패 양상이 달랐다. 아래 마지막 행은 송장과 배송지를 기준으로 삼아 필자가 직접 실행한 비교값이다.

| 실행 | SQL이 적용한 기준 | 관찰 결과 |
| :--- | :--- | :--- |
| 한국어 Chat | 주문 수량×단가, 지역 제한 없음 | 4,544 |
| 같은 한국어 문장의 대화 ID 없는 API 호출 | 주문 수량×단가, 고객의 우편 도시로 주 필터 적용 | 512.0 |
| 공식 영문 예제 | 송장 연락 담당자와 주 레코드의 최종 수정자를 사람 테이블로 연결 | 매출 값이 비어 있음 |
| 직접 작성한 기준 SQL | 송장 → 고객 → 배송 도시 → 주 | $588.80, 송장 항목 3건 |

영문 질의에 사용된 두 외래 키는 원본 DB에 실제로 있었다. 그 관계가 나타내는 것은 송장의 연락 담당자와 주 정보의 최종 수정자다. 배송 지역과는 무관하다. 반대로 송장·배송지 기준에 필요한 `customers.deliverycityid → cities.cityid` 역시 원본 DB에 있었지만, 실험에서 생성된 의미 관계 85개에는 포함되지 않았다. 조인이 실행된다는 사실만으로 업무적으로 올바른 관계를 선택했는지 확인하기 어려운 이유다.

이 샘플에는 주문과 송장, 우편지와 배송지가 함께 있고 실험에서는 공식 매출 계산식과 지역 기준을 인증하지 않았다. 한국어로 입력해 실행할 수 있다는 점과 핵심 조건이 보존되는지는 각각 확인해야 한다. 이 비교에서는 언어뿐 아니라 호출 경로도 달랐으므로, 결과 차이의 원인을 한국어로 특정하거나 같은 조건에서의 반복 실행 일관성을 판단하기는 어렵다. 관계를 보완하고 인증한 뒤의 정확도 역시 이번 실험에서는 측정하지 않았다.

## 현업에서 먼저 적용할 수 있는 범위

실험에서 확인한 활용처는 **메타데이터 탐색과 의미 모델 초안 작성**이다. 분석가가 생소한 DB에서 관련 테이블을 찾고, 데이터 모델러가 컬럼 설명과 관계 후보를 검토하는 데 쓸 수 있다. 텍스트 설명, 속성, 그래프, 질의를 한 화면 흐름에서 오갈 수 있어 관계를 정의한 사람이 그 정의가 실제 질문에 어떻게 쓰이는지 확인하기도 쉽다. 초안 생성 속도는 측정했지만 기존 문서화 방식 대비 사람의 검토 시간이 얼마나 줄어드는지는 측정하지 않았다.

자연어 질의는 업무 범위를 제한한 파일럿부터 시작할 만하다. 예를 들어 영업 운영팀이 승인된 판매 데이터 마트에 접속해 제품별 송장 매출을 조회하는 범위라면, 공식 BI 리포트와 SQL을 대조할 수 있고 결과를 검토할 담당자도 명확하다. 재무 결산, 대외 보고, 후속 조치를 자동으로 실행하는 에이전트처럼 오류의 영향이 큰 용도에는 승인된 지표와 필수 조건 보존을 확인하는 절차가 필요하다. 지역처럼 답변 범위를 바꾸는 조건을 처리할 수 없으면, 숫자를 계속 내보내기 전에 사용자에게 기준을 확인하거나 답변을 보류하도록 설계해야 한다.

업무 에이전트와 연결할 때는 REST API와 읽기 전용 MCP 도구를 검토할 수 있다. 프로젝트 문서에는 용어 검색, 답변 가능성 점검, 질문 실행 등이 안내돼 있다. 이번 실험은 웹 UI와 백엔드 질의까지 확인했다. MCP를 운영에 붙인다면 호출 사용자 권한이 원본 DB의 행·컬럼 접근 범위에 어떻게 적용되는지 실제 계정으로 점검해야 한다.

## 운영 환경에서 확인할 연결과 모델 제약

공식 문서는 PostgreSQL, MySQL, Databricks, Snowflake, ClickHouse, Trino, Apache Kyuubi, HeavyDB, DuckDB, SQLite 연결을 안내한다. 실험에서 사용한 엔진은 PostgreSQL이다. Trino를 통해 Impala–Kudu 데이터를 조회하는 조직이라면, 해당 데이터가 Trino에 테이블로 노출되고 Auto Ontology 계정으로 스키마 조회와 읽기 실행이 가능한지부터 확인할 수 있다. 실제 연결 조합에서는 타입, 식별자 대소문자, 샘플링, 조인 SQL과 원본 시스템에 전달되는 쿼리 범위까지 시험해야 한다.

모델 연동에는 추론과 SQL 작성, 의도 분류 등 비교적 가벼운 처리, 임베딩, 일부 컴파일 단계의 리랭킹에 맞는 API가 필요하다. 이번 NVIDIA 호스팅 조합에서도 기본 배치 32·동시성 32의 임베딩 요청이 HTTP 500으로 실패했다. 각각 1로 낮추자 640개 임베딩을 약 242초에 만들 수 있었다. 구조화 출력에서는 클라이언트가 보낸 `guided_json`을 호스팅 API가 거부했다. 동일한 NVIDIA 모델과 엔드포인트를 OpenAI 호환 클라이언트의 함수 호출 방식으로 연결해 실험을 계속했다. 이 수치와 오류는 사용한 버전과 모델 조합에서 관찰한 결과다. 실제 운영 규모를 가늠하려면 생성·재컴파일 시간, 질의 지연, 모델 호출 비용을 대상 스키마와 예상 동시 사용자 수에 맞춰 측정해야 한다.

Apache 2.0으로 소스가 공개돼 있어 수집, 모델 호출, SQL 검증을 추적하고 수정할 수 있었다. 자체 모델이나 사내 게이트웨이를 고려한다면 API 주소를 연결한 뒤 구조화 출력, 임베딩 차원, 리랭킹 지원, 응답 품질과 처리량을 확인해야 한다. NVIDIA NIM은 자체 인프라에서 필요한 모델 API를 운영하는 선택지다. 의미 모델을 다른 도구와 교환할 때는 Apache Ossie YAML 가져오기·내보내기를 검토할 수 있다. 일반 설치와 이 글의 실험에는 Ossie 교환 과정이 필요 없었으며, 실제 전환에서는 지표와 조인 정의가 양쪽에서 어떻게 대응하는지 확인할 필요가 있다.

호스팅 모델을 쓰면 호출 단계와 설정에 따라 테이블·컬럼 이름, 제한된 샘플값, 질문과 검색 문맥이 외부 엔드포인트에 전달될 수 있다. 회사 DB에 직접 연결할 수 없는 개발 환경이라면, 공개 데이터나 반출 승인을 받은 합성 샘플에 주문·송장과 우편지·배송지처럼 구분할 역할을 남겨두고 UI와 관계 생성 흐름을 먼저 시험할 수 있다. 실제 데이터에 대한 인증은 내부 환경에서 진행한다. 차단망에서는 앱의 컨테이너와 패키지 외에 내부에서 호출 가능한 모델 서비스, 모델 반입과 업데이트 절차, 처리량과 장애 대응 체계까지 준비해야 한다.

연결 자격 증명 관리도 배포의 일부다. 공식 문서에 따르면 Vault를 구성하지 않으면 UI에서 등록한 연결의 자격 증명이 메타데이터 PostgreSQL에 평문으로 저장된다. 백엔드와 수집 서비스는 사설 네트워크에 두고, 운영 DB에는 허용된 뷰만 읽는 최소 권한 계정을 사용하는 구성이 적절하다. 사용자별 접근 범위, 쿼리 시간과 결과 행 수 제한, 감사 기록, 메타데이터와 샘플의 외부 전송 범위는 파일럿 단계부터 확인할 항목이다.

## 파일럿에 필요한 업무 정의와 검증 기준

기업에서 시작한다면 영업이나 재고처럼 담당자가 분명한 업무 영역 하나를 고른다. 이번 사례의 판매 데이터라면 기존 BI에서 쓰는 송장 매출 계산식과 배송지 기준을 가져오고, 취소·반품 포함 여부와 집계 날짜의 기준을 현업과 합의하는 것으로 시작할 수 있다. 기존 카탈로그나 지표 사전, 검토를 거친 SQL이 있으면 용어와 계산식을 검증할 근거로 쓴다. 감사용 관계는 업무 조인과 구분하고, 누락된 배송지 관계는 업무 담당자가 확인한다.

1. **정답을 먼저 준비한다.** 대표 질문에 기준 SQL과 예상값을 붙인다. 한국어 표현 변형, 주소 역할이 모호한 질문, 결과가 비어야 하는 질문, 권한 때문에 답할 수 없는 질문도 포함한다.
2. **인증과 평가를 연결한다.** 데이터 모델러가 용어와 조인을 검토하고 업무 담당자가 지표를 승인한다. 같은 모델에서 스키마만 썼을 때, 자동 생성한 의미 계층을 썼을 때, 사람이 인증한 뒤를 비교하면 개선이 어디서 나왔는지 볼 수 있다. NVIDIA 평가 도구는 스키마만 쓰는 구성과 의미 계층을 쓰는 구성을 비교하는 출발점을 제공한다.
3. **운영 판단 기준을 정한다.** 실행 결과의 정확도에 더해 필수 조건 보존율, 근거가 부족할 때의 응답 보류, 권한 테스트 결과, 승인과 수정에 드는 시간을 본다. 스키마나 모델, 앱 버전이 바뀌면 대표 질문으로 회귀를 확인한다. 재컴파일 후 주요 조인 경로도 다시 확인할 항목이다.

공개 샘플에서 발견한 가장 실용적인 지점은 숫자와 SQL을 함께 보며 업무 정의의 공백을 찾을 수 있다는 점이었다. 지역 조건이 빠진 4,544라는 값은 어떤 지표와 관계를 먼저 손봐야 할지 보여줬다. 현업 파일럿의 성과는 그렇게 찾아낸 문제를 고친 뒤, 같은 업무 질문에 기존 BI와 일치하는 답을 낼 수 있는지로 판단할 수 있다.
